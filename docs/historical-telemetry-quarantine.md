# Historical telemetry quarantine

Migration `0005_quarantine_historical_telemetry` preserves pre-upgrade runtime events, model usage costs, and route assignments, but clears their tenant assignments. Existing assignments could come from a Guardrail owner, Router owner, a fallback tenant, or an unauthenticated Runner claim. Even an Endpoint-shaped record does not establish which authenticated Runner sent it. A testing cost can exist without a corresponding runtime event. Consequently, the migration does not treat any historical assignment as proven ownership.

Records remain available through platform-wide queries. Tenant-scoped event, cost, and route distribution queries omit these records, so tenant historical dashboards and cost totals will decrease at upgrade. This is intentional; missing caller identity cannot be reconstructed by guessing. The existing deletion-impact safety check is an exception: it aggregates all matching events, including quarantined events, and currently exposes the count and latest timestamp to the resource owner. That aggregate disclosure remains to be fixed without weakening the global deletion safety check. New records continue to use the current ingestion rules and are subject to the remaining limitations documented in the implementation progress log.

For each previously assigned record, the migration records its type, ID, and old tenant ID in `historical_telemetry_attribution`. This table is internal database evidence, not an authorization source. Platform operators may inspect it with the original record and independent trustworthy evidence. The old tenant ID alone is not evidence that restoration is safe. There is no tenant-facing API or automated reassignment: restoring an assignment requires an operator's explicit, individually justified database action after verifying the actual caller and any related event, cost, and route records. A former assignment must not be bulk-restored merely to recover dashboard totals. Record-level retention/deletion of the auxiliary evidence and a supported review/remediation workflow remain implementation work.

The migration takes write-conflicting locks on all three telemetry tables while preserving assignments and clearing ownership, and records a checkpoint so replay does not quarantine newer records. A later completion for a quarantined historical route assignment can update its outcome when all stored routing identity and decision-time fields match, but it remains quarantined. The historical assignment did not retain an authenticated Runner identity; matching these fields is not proof that the completion's sender is trustworthy. Pool-scoped internal HTTP authentication and stronger invocation provenance are still needed. Historical runtime-event enrichments and cost replays do not restore quarantined ownership.

Plan the upgrade for the size of the existing telemetry tables and back up the database. **Stop all old Controller writers before migration and keep them stopped:** a mixed-version deployment or rollback to older ingestion code can write unsafe assignments after the checkpoint. Migration alone cannot fence stale writers. No current local runtime has been upgraded by this change.
