# 系统状态 503 排查与统计数据扩展方案

本机部署的 `/api/v1/system/status` 503 已复现，直接原因是 Controller 判定 Runner 离线。接口响应仅 1,284 字节，约 76 ms，当前证据不支持“状态接口携带的历史数据太多”这一解释。代码中还确认了失效控制会话不能主动恢复的路径，应优先修复；统计查询随事件量增长的成本则需要单独治理。

本文记录排查结果、已实现的修复与后续数据设计。P0 和 P1 的统一统计并发预算已在工作区实现，尚未部署；没有迁移或删除数据。原始观测时间为 2026 年 11 月 11 日 10:10—10:15（Asia/Shanghai），范围是本机 OrbStack 的 `tali` 部署。部署提交与工作区 HEAD 均为 `570c613f5c7251fac4a2da64b994d16db0b8071e`。

## 本次修复范围

- 失效会话在消息处理、周期协调或调度前检查时，移除内存连接并结束 gRPC 流，利用 Runner 已有逻辑重新连接。异步检查后核对连接对象身份，避免旧会话删除同 runnerId/bootId 的替代连接。
- 首页独立查询平台状态、统计和事件；状态请求设置 3 s 超时并接收取消信号。有效的业务 503 展示真实原因，代理 HTML 503、非法响应和超时展示“状态未知”，不会阻塞其他区块。状态和事件可独立重试。
- 所有项目与平台的未缓存统计查询共用每个 Controller 进程最多 2 个分析任务的预算，超额沿用 `metrics_busy` 错误。项目请求继续逐次检查实时权限，不共享旧结果；平台的缓存和同请求合并保留。此限制不是整个集群的连接数上限。现有 `boundedRead` 已提供默认 20 s 的分析 SQL 读预算，连接池另有默认 30 s 单语句超时；这些超时并非本轮新增。

最初恢复修复保持后端 HTTP 接口与 200/503 语义兼容。后续按请求增长问题实施了首页 overview 时间桶和读路径分离，见本文末节；独立分析连接池、组件/费用预聚合仍未实施。

## 已确认的恢复缺陷

修复前的流程存在以下闭环：

1. 默认每 10 s 上报心跳，30 s 未更新即满足离线阈值。
2. `markStaleRunnersOffline()` 将 Runner 和控制会话写为已断开。
3. 后续消息进入 `handleMessage()`；`runnerControlSessions.isCurrent()` 返回 false。
4. 处理器直接 `return null`，不接收心跳，也不结束 gRPC 流。
5. 后台 `reconcileOnce()` 对失效会话同样直接返回。Runner 无法通过现有流恢复，也可能继续认为自己已连接。

修复前的内存复现实验：失效会话连续发送 3 次心跳，所有权检查执行 3 次，心跳写入 0 次，流关闭 0 次，连接仍保留在内存注册表。这证实了“已被标记离线后，恢复通信仍不能恢复状态”的代码路径；最初心跳为何停止尚未确定。

相关实现：

- [离线清理与心跳写入](../controller/server/services/control-plane.ts)：`recordHeartbeat`、`markStaleRunnersOffline`。
- [控制会话有效性](../controller/server/services/runner-control-sessions.ts)：`isCurrent`。
- [控制消息与周期协调](../controller/server/control-channel/control-server.ts)：`handleMessage`、`reconcileOnce`。
- [Runner 重连与同步状态](../runner/control_client.py)：`run`、`_connect_once`、`synchronized`。

本次已修复失效会话处理：收到持久化失效结果时，移除该会话的内存调度资格，结束其 gRPC 流，触发 Runner 现有重连与重新注册。周期协调执行相同处理，以覆盖没有后续消息的连接。不能只删除数据库的离线条件或允许旧心跳复活会话，那会破坏已替换会话的隔离。

关闭时必须绑定具体 `sessionId` 和连接对象，在异步数据库检查后再次核对对象身份。旧连接的清理不能删除同 runnerId、同 bootId 的新连接。保持现有停机排空语义：已接收报告按原规则完成，失效流不再调度新任务。Runner 的发送任务、心跳任务需要受监督；后续可增加应用层心跳确认与超时重连，避免仅依赖 TCP 仍连接这一信号。

## 首页为何需要独立处理

侧栏 Logo 对具备 runtime 权限的项目用户指向 Dashboard。修复前 `getMetrics()` 使用 `Promise.all` 同时等待统计和系统状态，状态请求没有显式超时，也不接收页面的取消信号；本次已拆开。

但 `getControllerSystemStatus()` 已接受 HTTP 200 和 503 的 JSON；因此有效的业务状态 503 本身不会使当前代码的统计 Promise 失败。状态请求挂起、响应为代理 HTML、JSON 不合法，或统计接口本身失败，才会触发相应加载问题。用户报告的页面失败仍需浏览器 Network 与控制台证据定位，不能由 503 单独推定。

首页应有三个独立查询：状态、统计摘要/趋势、事件列表。每块独立显示 loading/error，状态未知不伪装健康，统计失败不补零；有旧数据则显示更新时间。状态请求设置约 3 s 的 UI 超时并接收取消信号，重试有上限。后端同时执行数据库级超时和并发限制，不能仅让浏览器停止等待而 SQL 继续运行。

保留 `/health/live` 和 `/health/ready` 的现有部署探针用途；保留 `/system/status` 的 200/503 兼容语义。系统不可用时仍应允许用户进入管理页面查看故障。

## 数据增长影响在哪里

`system/status` 查询的是 Runner、路由发布计划和模型配置，没有查询 `runtime_event`。配置数量和历史 Runner 记录增加会提高它的内部查询成本，但接口返回并非历史请求集合。可以用仅含状态字段的投影、池级聚合、按配置 generation 缓存模型依赖，替代全量实例和完整配置加载；动态心跳新鲜度仍按当前时间计算。

更明显的扩展性风险在 [runtime-metrics.ts](../controller/server/services/runtime-metrics.ts)：

- 为计算前期对比窗口，30 d 查询覆盖约 60 d 原始事件。
- 一个请求同时计算周期、Guardrail、调用方、版本、引擎和趋势等维度，并展开 trace、findings JSON。
- 多处对原始延迟进行精确百分位排序；虽然返回的是聚合值，数据库工作量仍随匹配事件数及 trace 长度增长。
- 目前已按窗口使用 1 m、15 m、1 h、6 h、1 d 的展示粒度，但仍从原始事件计算。只增大图表间隔无法消除扫描和 JSON 展开。
- 修复前 `ControlPlaneService.runtimeMetrics()` 的项目请求绕过最多 2 个任务限制；本次已统一并发预算。项目请求仍不使用 10 s 缓存或同请求合并，以保持资源授权实时生效。
- 统计和心跳共用数据库池；当前生产配置上限为 20 个连接。重查询并发可以间接延迟心跳，这是风险链路，尚未被此次现场证据证实。

## 接口拆分建议

以下新增接口属于实施设计；现有鉴权和项目选择方式保持一致。

| 接口 | 内容与访问方式 | 预算目标 |
| --- | --- | --- |
| 现有 `GET /api/v1/system/status` | 保持兼容的全局业务状态；仅返回少量汇总 | 本机同等环境 p95 < 200 ms，响应 < 8 KB |
| 现有 `GET /api/v1/system/health` | 项目页独立获取组件健康；实施时核对池、模型依赖的项目范围 | 不依赖历史事件表；不得把默认池健康当作所有项目健康 |
| 新增 `GET /api/v1/telemetry/summary` | 总量、结果分布、错误率、延迟分布、前期比较 | p95 < 500 ms；缺失聚合时返回明确未就绪 |
| 新增 `GET /api/v1/telemetry/trends` | `window`、受限 `interval`、`groupBy`；默认全局一条曲线 | 最多 200 点/曲线、20 条曲线；默认响应 < 100 KB |
| 新增 `GET /api/v1/telemetry/breakdown` | 用户展开诊断后才查询组件、版本、调用方等；分页 | 独立并发预算，不阻塞 summary |
| 现有 `GET /api/v1/telemetry/events` 与 `/:id` | 列表用游标；详情按需读取 trace、证据与内容 | 延续现有有界分页及内容权限 |

Top N 趋势必须返回选择规则、`other` 和截断标记，不能静默丢掉其他系列。总览 summary 始终来自全部匹配事件，不由 Top N 相加得出。breakdown 的分页在最终分组聚合之后执行，不能把原始事件先 LIMIT 再当作全量统计。

保留旧 `/telemetry/metrics` 作为迁移期兼容入口，逐步从新查询组合；首页切换后不再预取所有诊断维度。仅拆 HTTP 接口而复用同一全量计算函数，不会降低负载。

先为所有项目请求补上统一的分析查询并发预算，再做缓存。缓存键包括项目、筛选条件、窗口锚点及访问范围版本；每次请求先检查实时授权。当前绕过缓存是为了避免权限撤销后读取旧数据，不能简单移除这条分支，或只按 projectId 共享含资源名称的结果。分析连接池与心跳/控制连接池分开预算，总连接数仍受数据库容量约束。

## 数据模型

建议先继续使用 PostgreSQL，通过持久化预聚合减少每次读原始事件的成本。当前 40 MB 的现场规模不足以支持直接引入另一套分析数据库的复杂度。

| 表或逻辑数据集 | 最小粒度和字段 | 用途 |
| --- | --- | --- |
| `runtime_event` | 保留稳定 eventId、projectId、发生/接收时间、资源 ID、执行结果、耗时 | 事实来源、追查与重建 |
| `runtime_event_detail` | eventId 关联 trace、findings 的详细证据、内容等大字段 | 详情读取；热统计不反复解析大 JSON |
| `runtime_metric_rollup` | `projection_version, project_id, resolution, bucket_start, dimension_kind, dimension_key` 为唯一键；计数、耗时 count/sum/max、直方图、updatedAt | 摘要与趋势 |
| `runtime_component_rollup` | 时间桶、项目、组件类型/ID/版本、必要的资源范围；调用次数、错误次数、耗时直方图 | 组件诊断，不与首页查询绑定 |
| `runtime_metric_work` 与应用账本 | 事件 ID、投影版本、处理状态；账本唯一键为投影版本和 eventId | 可靠处理、重试去重及回填 |

维度首批只支持项目总览、Guardrail、Router，以及当前 API 允许的 Guardrail+Router 联合筛选。避免将 requestId、runnerId、任意标签都加入聚合键。维度编码采用有类型的规范化结构，避免 NULL 唯一键或分隔符碰撞。权限若限制到资源子集，查询必须使用对应资源投影；项目总览预聚合只可提供给拥有相应完整可见范围的请求。

指标口径保持当前完成的 Guardrail 检查次数，不能在迁移时悄悄改成去重 HTTP 请求次数。明确输入、输出检查与 call-completion 事件的计入规则，固定 `executionError`、timeout、fail-closed 的归一化版本。计数使用 bigint；JS/API 对超过安全整数范围的行为单独定义。

计数和耗时总和可相加；P95/P99 不可对每分钟的百分位取平均。存储可合并的直方图桶，再从合并结果估算百分位；桶边界带版本，包含 overflow 和业务 SLO 边界。响应标明 `quantile_method`、桶精度及溢出情况。这会将当前精确百分位改为近似值，需在切换前验证误差与产品展示口径。[Prometheus 官方说明](https://prometheus.io/docs/practices/histograms/)解释了百分位与可聚合直方图的区别。

`degraded_endpoints`、`affected_traces` 等去重计数不能跨时间桶直接求和。错误 Endpoint 可从 endpoint 维度状态去重；跨桶请求数若要求精确，则使用独立去重事实查询并放在按需诊断中。除非接口明确标注近似，否则不能用近似集合替换当前精确值。版本/checksum 等高基数列表也移到分页诊断接口。

## 时间粒度和保留期

以下是建议默认值，删除任务仅在回填、重建能力及保留政策确认后启用。

| 数据 | 建议保留期 | 说明 |
| --- | --- | --- |
| 原始事件与详情 | 30 d，可配置 | 事件追查；敏感内容可采用更短周期 |
| 1 m 聚合 | 7 d | 近期趋势、窗口边界处理 |
| 15 m 聚合 | 90 d | 支持最长 30 d 当前窗口和 30 d 对比窗口 |
| 1 h 聚合 | 400 d | 长期趋势 |

展示继续使用 1 h→1 m、24 h→15 m、7 d→1 h、15 d→6 h、30 d→1 d，避免无必要的交互变化。粗粒度从预聚合合并得到，不重新扫描所有原始 trace。

一期窗口统一按所用存储桶边界对齐，并返回真实 `window_start`、`window_end`、时区 UTC、数据更新时间和 `complete_through`。当前窗口与对比窗口等长且互不重叠。若以后支持任意秒级边界，只在两端用更细粒度或有界原始查询补齐；不能把边界整桶悄悄算入。数据尚未聚合时返回 lag/partial，不能标成完整或用零填补缺失。

未来当原始表规模与维护成本确实需要时，再按发生时间做日/周分区和归档。PostgreSQL 的分区主键/唯一约束必须包含分区键；现有 eventId 全局去重不能在迁移时丢失，需独立去重账本及明确的历史重放期限。[PostgreSQL 分区文档](https://www.postgresql.org/docs/current/ddl-partitioning.html)说明了这一限制与分区删除的收益。

## 增量处理与一致性

1. 原始事件成功插入后，在同一事务为新 eventId 写入持久化工作项。遥测重复上传依赖现有事件唯一约束，不重复生成贡献。
2. worker 以有界批次领取工作，先按投影版本/eventId 插入应用账本。仅对成功插入的新账本记录计算贡献；多个时间层级的聚合更新、账本及工作项完成标记在同一事务提交。
3. 同一批次先按聚合键合并，再按固定键顺序更新，减少项目总览热点锁争用。失败事务整体回滚，重试不会重复累加。不能仅用自增序号最大值作为完成水位，避免漏掉较晚提交的较小序号。
4. 按 occurredAt 分桶，按持久化工作项处理；迟到事件更新仍保留的历史桶和相应层级。接收时间用于观测延迟，不能代替事件时间。
5. 超出支持重放期限的事件按明确规则拒绝或进入修复队列。去重账本保留期不得短于允许重放期限，未处理完成的原始事实不得被保留任务删除。
6. 在线事件与历史回填走同一投影去重规则；按项目和时间分批回填，限速执行。原始明细已过期的数据只能由已保存的更细聚合重建，不能声称还能恢复完整 trace。
7. 在删除、订正原始业务数据时定义聚合撤销或受影响桶重算流程。工作项必须保存必要贡献或保证事件存活至应用完成，避免原始行先删除导致静默漏计。

例如，假设 100 次检查/s，则一天有 864 万条原始检查；一个项目总览维度的 1 m 聚合每天最多 1,440 桶，24 h 的 15 m 图表只有 96 个完整桶。这个差距说明预聚合的收益，实际空间压缩率仍取决于维度数、直方图大小和事件大小。

## 实施顺序与验收

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| P0 | 失效会话主动断流重连；状态/统计/事件独立加载；状态超时与取消 | 心跳间断后恢复通信，Runner 自动注册并恢复业务状态；旧流不能影响新会话；状态 503/超时/非法响应均不阻塞其他区块 |
| P1 | 所有项目统计并发控制；权限安全的缓存与请求合并；摘要/趋势/诊断拆分 | 并发查询不占满控制连接预算；撤权立即生效；首页不执行 trace 组件统计 |
| P2 | 预聚合表、worker、历史回填、双读对账、逐步切流 | 计数一致；分位误差符合选定桶精度；重试、乱序提交、迟到、重启、回填与写入重叠均不漏不重 |
| P3 | 根据实测启用保留任务、分区与归档 | 聚合水位与归档检查通过后才清理；旧 API 可回滚到保留范围内的查询 |

测试矩阵至少覆盖 1 万、100 万、1,000 万事件，短/长 trace，多 Guardrail/Router，1/10/50 个并发查看者，以及压测流量与浏览器查询同时发生。先在隔离数据库测试，记录冷/热查询 p95、查询计划与临时文件、连接排队、心跳年龄、聚合 lag 和响应大小。前述接口预算是待验收目标，不是本轮压测成绩。

## Runner 派生展示链路扩容审计（2026-11-11）

结论：存在扩容瓶颈，但需区分页面请求耗时、数据新鲜度和功能容量上限。大多数展示请求读取 Controller 保存的心跳或遥测，不会在打开页面时实时向所有 Runner 拉取数据。

- 心跳覆盖更新每个 runnerId 的最新状态，不因心跳次数增加历史行；状态查询主要随 Runner、Pool 和配置数量增长。
- 历史统计主要随所选窗口内事件数、trace/findings 长度和分组维度数增长。固定流量、固定窗口充分填满后，扫描行数不会仅因系统运行时间增加而无限增长，但总表体积仍影响索引、缓存和维护。
- “最后一次错误”等无时间范围查询、缺少匹配索引的日志分支，可能受历史总量影响。
- 数据新鲜度还取决于 Runner 待上传日志积压、上传吞吐、数据库写入和页面轮询等待；接口返回快不代表数据已经追平。

### 控制链路与上传链路

**心跳共享全局锁。** `recordHeartbeat` 在事务中取得 `traffic-router-bindings` 排他 advisory lock；配置投影 `desiredStateForPool`、离线处理也使用该锁。准入监控读取 inventory 持有同名共享锁。Runner 数量和配置规模增大后，这些工作可能互相等待。连接池为生产默认 20 个连接，控制和分析共用；默认锁等待超时为 5 s。需要观测锁等待和连接排队，不能把所有心跳延迟归因于历史事件，也不能直接删除保护配置/会话一致性的锁。

**上传并发有界，吞吐不随 Runner 数自动增加。** `TelemetryUploadAdmission` 默认每个 Controller 最多 4 个上传任务、每池最多 2 个，超额返回可重试 503。这能限制 Controller 在途负载，但同池增加 Runner 后仍需评估积压；它与 `/system/status` 的业务 503 是不同路径。

**Runner WAL 存在随积压放大的读写。** `runner/telemetry.py::_flush_once` 每批上传前读取整个 WAL，ACK 后再次读取、复制并重写全部剩余日志，还遍历剩余行计算字节数；批大小最多 1,000 并未限制单次文件处理量。文件 I/O 放在线程中，但持有与新增事件写入共用的异步锁。主 WAL 未找到总量上限，64 MiB 限制仅用于 rejected WAL。固定批大小下，单批工作量随积压字节数增长；若逐批清空一大段积压，累计文件处理量还会反复覆盖同一批未发送数据。

### 本轮验证证据及边界

数据库检查均在只读事务中执行，设置 5 s SQL 超时并回滚；没有写入压测数据。现场约有 3,623 条 runtime_event、3,623 条 route_assignment、6,708 条 model_usage_cost、1 个 Runner。

### 建议落地顺序

1. **先收敛现有查询。** Endpoint activity 支持单 ID 或受限 ID 集合并独立加载；按真实 executionStatus 条件建立错误索引；为失败调用列表补齐与作用域、排序及游标相符的索引或专用事件投影。状态接口仅查所需池级状态，避免全量实例；Guardrail 列表分页并批量取摘要。每处均用实际 SQL 计划验证，不能只新增一个名称相似的索引。
2. **消除 Runner 扩容和积压恢复的硬障碍。** 准入监控按池/项目分页，最新报告写入共享存储，带 runnerId/bootId/sessionId/sequence 和 TTL，保持旧会话不能覆盖新会话；小规模汇总与实例详情分离。WAL 改成有界分段的追加日志加持久化确认游标，ACK 后回收完整段，保留未确认事件和幂等重试；明确磁盘配额及满额背压策略，不能静默丢数据。
3. **再落地前述持久化聚合方案。** 摘要、趋势、诊断分别读取；粗粒度来自已计算时间桶，不反复展开原始 JSON。分析任务与心跳分开连接和并发预算；观察全局锁持有时间，再设计保持 generation/session 一致性的细化方案。
4. **补齐数据生命周期。** 仓库目前可见 route_assignment 的 30 d 清理逻辑；未找到 runtime_event / model_usage_cost 的自动保留任务，设置响应中的 retentionDays=30 不能证明已清理。结合回填水位、费用审计期限和去重账本，分批清理或按时间分区，不直接套用同一保留期删除所有表。

容量验收除前述事件规模矩阵外，应覆盖 1/32/33/100 个 Runner、31/32/33 个池、127/128/129 个项目、离线实例残留，以及未来双 Controller 下跨副本读取。分别记录页面 p95、扫描行数、连接/锁等待、心跳年龄、WAL 最旧事件年龄和补传追平时间。固定窗口流量不变而只增加窗口外历史数据时，摘要和分页列表也应保持近似稳定。

该审计轮次仅完成只读计划检查、临时文件实验和文档修订。后续按请求增长问题实施的修复如下；Runner/Project 数量相关限制不属于此次实施范围。

## 已实施：请求增长与遥测积压修复

以下修改已在工作区完成，尚未部署。没有修改运行实例的数据，也没有启用历史原始数据删除任务。

### 首页统计从原始扫描改为持久化时间桶

- `/api/v1/telemetry/metrics?view=overview` 读取 `runtime_overview_bucket`；原有默认接口继续提供完整诊断和精确百分位。
- 表按项目、Guardrail、Router、Endpoint 及时间分组，保存精确计数和有界延迟直方图，分别维护 1 m、15 m、1 h 三档。首页及 Guardrail 请求速率采用 overview，不再每次刷新展开原始 trace/findings。
- PostgreSQL statement trigger 在事件写入事务中更新聚合，只累计真正插入的新行。重复上传不增加计数，内容补充不改变指标，订正和删除应用相反贡献；事务回滚也回滚聚合。无需依赖后台 worker 的处理水位。
- 普通遥测和内容补充均以最多 50 个不同 eventId 批量写入，减少数据库往返和聚合更新次数；遇到重复 ID 切分批次，保持先写入、后补充的原有顺序。现有归属验证和内容不可覆盖规则保留。
- 当前窗口与比较窗口按整分钟边界等长切分，`window_end` 最多超前当前时间不到一分钟。较长窗口的内部使用粗桶，两个窗口各自的边缘使用分钟桶，避免整小时边界多计或漏计。响应返回真实起止时间。
- 首页分位数取可合并直方图的桶上界，误差上限为真实分位值的 5% 加 1 ms；2,500/5,000 ms SLO 边界单独保留。响应包含 `latency_method=histogram_5pct`，卡片、图表说明和排查摘要标明估算；评估计数保持精确。overview 不计算组件、findings、费用等诊断数据，不能将该视图里的空诊断字段当成完整诊断结论。

同一时间和资源范围内，1,000 条与 50,000 条事件均只产生 3 行时间桶。每行直方图的键数也受整数毫秒时长范围与固定桶边界约束，不按 eventId/requestId 增长。查询工作量主要取决于窗口长度和资源维度，不再随重复请求条数增加而扫描同等数量的原始事件。

### 移除页面隐式触发的重查询

- 新增 `GET /api/v1/guardrails?view=options`，仅返回实时可见的 `id/name`。首页筛选器、日志页筛选器和侧栏计数使用它，不再因获取名称而统计当月原始费用。
- 侧栏 Endpoint 数量仅查询定义，不再隐式读取全部 activity。
- Endpoint activity 支持 `endpointId`，详情和设置更新仅请求对应端点；保留当前权限过滤。平台缓存按端点区分且最多 16 项，项目请求继续实时检查权限。
- Endpoint activity 与 metrics 共用每进程最多 2 个分析任务的预算，仍保留 SQL 读预算；没有将未授权项目结果放入共享缓存。

### 事件分页与 Endpoint 索引

- 运行事件和失败调用各自在完整筛选条件及游标之后排序、取 `limit+1`，再合并为最终一页。不能只在 UNION 外层 LIMIT，也不能先截断未过滤事件。
- 为失败调用增加与时间、`call:` ID 排序匹配的全局、项目和 Router 部分索引；项目事件时间索引补齐 ID。
- Endpoint 错误索引改用真实 `metadata.executionStatus` 条件；近期活动和错误索引覆盖 requestId 等查询字段，减少读取大 metadata/TOAST 的需求。
- 十万条 route_assignment 的真实查询计划验证：常规第一页的失败调用分支使用匹配索引，读取不超过 51 行。分页同时间戳、旧严重事件过滤、真实失败调用与 checkpoint 混合分页均通过回归。

### Runner WAL 按批读取与确认

- 保持现有 `runtime-events.wal` 文件，增加与文件 inode 绑定的持久化字节游标。启动时仅流式扫描待确认后缀一次；每批读取最多 1,000 条并设置读取字节预算，不再加载整个积压到内存。
- 只有有效 ACK 或成功写入隔离日志后才推进游标。上传期间新增的尾部保留，重启恢复从已确认位置继续；游标提交失败时重试原批次。
- 已确认前缀至少 8 MiB 且占文件一半后才流式整理；完全清空时回收文件。累计复制成本摊销为线性，仍可能有偶发整理成本。替换文件与旧游标通过 inode 区分，整理中断不会跳过新文件中的待发送事件。
