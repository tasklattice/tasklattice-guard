# Guardrail Validation 依赖状态与提示规范

## 目标与范围

Guardrail 管理员打开详情页即可知道当前草稿能否进行 Validation、具体缺少哪项依赖，以及如何修复。已保存的旧草稿也必须检查，不能依赖创建页已经做过检查。

本规范的提示针对当前可编辑草稿，不代表已发布版本或历史 Validation 的执行状态。保留现有数据库配置，不自动移除 Policy，不自动发布或改变流量。

## 状态语义

| 状态 | 展示 | Validation 行为 | 修复路径 |
| --- | --- | --- | --- |
| 已确认模型未绑定、能力验证失败／未验证、尚未激活 | 红色边框、浅红背景、错误图标与明确标题 | 禁用详情页所有运行、重新运行和确认入口；提交回调再次检查 | 编辑并移除受影响 Policy，或完成模型绑定、能力验证及 Runner 启用 |
| 模型正在激活 | 红色阻断框，明确“尚未完成启用” | 等待就绪 | 重新检查依赖 |
| 模型配置或 Policy 目录读取失败 | 黄色边框、浅黄背景，提示“状态未能确认” | 暂停提交，避免将未知状态当成就绪 | 重试读取，不声称模型未配置 |
| 自定义 Policy 的依赖无法从元数据确定 | 黄色注意框 | 单独这一项不阻断，交给现有执行验证 | 明确列出待确认 Policy，不声称其无需模型 |
| 正在首次检查 | 中性色与加载图标 | 暂停提交 | 请求完成后自动更新 |
| 选中依赖均已验证并在 Runner 激活，或全部为本地能力 | 默认不显示提示框 | 解除依赖阻断，其他用例／权限／发布条件继续生效 | 无需操作；不能显示“Validation 已通过” |

绿色仅用于已有成功证据，例如 Validation 已通过。依赖就绪不等于 Guardrail 行为验证通过，因此默认采用无色正常状态。

## 内容与位置

提示放在详情页标题、操作栏下方，所有页签上方，打开 Runtime 默认页签时也能看见。每条错误包含：

1. 影响：当前草稿无法进行 Validation。
2. 原因：能力、请求／响应方向、具体依赖状态。
3. 范围：受影响的 Policy 名称。
4. 操作：编辑移除／重新检查依赖。

不得仅显示“失败”“0%”或内部异常类型。长名称和错误正文换行，不依赖颜色单独传递状态。错误用 `role=alert`，加载及注意用 `role=status`；操作按钮至少 44px 高。

## 依赖判定与恢复

- 复用统一依赖解析：基于选中 Policy 的固定版本、启用规则与方向解析，不用行业分类推断模型依赖。
- 未选中、不执行的能力不产生错误；本地规则不要求模型。
- 只有活动配置中的对应能力具有通过的 `nemo-rail-v1` 验证证据才算就绪。普通聊天连通性测试、草稿通过验证均不足。
- 已有有效活动配置时，更新草稿的失败不替代活动证据。
- 每 10 秒刷新需要的模型状态；手动重试与保存 Policy 后重新计算。
- 此次实现是详情页和编辑页的前置引导，不替代服务端的编译、执行与发布校验，也不宣称其他独立 Validation 页面已受此 UI 门禁覆盖。

## 历史失败详情

详情必须显示服务端记录的 `failure_reason`，保留原始换行。没有原因且没有用例结果的失败记录，黄色提示“未记录原始原因，无法从该记录确定”。当前草稿依赖错误与历史失败分别展示，不把当前状态当成历史根因，也不改写历史记录。

## 验收

- 目标详情页打开即报红，并显示具体 Topic Control 依赖及移除入口。
- Validation 页签、草稿页、历史记录重新运行和确认提交均不能绕过阻断。
- 在编辑面板暂存移除后，依赖阻断消失；取消不持久化，保存只更新用户确认的草稿。
- 网络错误用黄色未知状态，可重试恢复；全部本地规则无需模型查询。
- 桌面和窄屏均无横向溢出，错误及按钮可见；类型检查、状态和修复路径测试通过。

## Topic Control Policy v2：独立 Rule

- `builtin-topic-safety@2.0.0` 是一个 Policy，包含 `topic/denylist` 和 `topic/allowlist` 两条 Rule。Guardrail 绑定 Policy，Rule 开关存放在 `enabled_rule_ids`。
- 配置保存在该绑定的 `parameter_values`：`denied_topics`、`allowed_topics`（每行一项）、`topic_mode`（`strict` 或 `permissive`，默认宽松）。v2 不读取 Guardrail 根级名单。
- 黑名单启用时必须填写拒绝话题，命中始终 `reject`，优先于白名单；白名单启用时，严格模式要求非空允许名单并拦截未匹配任务，宽松模式允许未匹配任务继续接受其他 Policy 检查。
- Rule 可独立关闭，关闭后保留参数但不编译该 Rule，不调用其模型。至少启用一条 Rule；要关闭整个能力，移除 Policy。
- 意图／上传文档分析仅是 Policy 内的配置 Helper。先展示建议，再由用户应用名单；不自动切换 Rule、不修改模式、不添加或移除其他 Policy。没有可用 Topic Control 模型时，意图输入和文档入口一起禁用。
- NeMo 原生 Topic Flow 共享一份提示词，因此 v2 采用具有独立 binding 参数的 Action，避免两条 Rule 共用边界。执行顺序固定为黑名单、白名单，日志归属到对应 Rule ID。
- v1 定义作为历史版本保留，已有绑定及已发布 Artifact 不改写。编辑旧草稿时可显式升级为 v2；保存前只修改编辑器状态。升级会把根级名单复制到 Policy 参数；有黑名单时启用黑名单 Rule，并采用绝对拒绝语义。
