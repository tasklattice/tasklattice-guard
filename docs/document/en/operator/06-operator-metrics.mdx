Both Controller and Runner expose metrics. Business statistics APIs and Prometheus scrapes have different purposes and credentials.

**Business statistics JSON**

GET `/api/v1/telemetry/metrics` on this Controller. Use a personal token with `runtime:read` or a browser session. Filter by window, `guardrailId`, and `routerId`. Statistics aggregate reported runtime events.

**Router traffic statistics**

GET `/api/v1/routers/{id}/traffic-distribution`, also available per Route. Requires `routers:read` and reports historical traffic, not configuration rollout status.

**Controller /metrics**

Scrape the Controller HTTP address. When `CONTROLLER_METRICS_TOKEN` is configured, send that Bearer token, not a personal Access Token.

**Runner /metrics**

Scrape each Runner HTTP address (default container port 8091). When `GUARD_METRICS_TOKEN` is configured, send that Bearer token. Use your deployed Runner addresses.


> Links use this Controller’s address, without fixed localhost ports. Opening a protected Prometheus URL directly returns 401; configure the scraper’s Authorization header. Check `data_availability` when traffic or execution evidence is missing.

## Troubleshooting order

Check routing and version first, then Rail, Action, provider, and capacity.

1. **Identity and route** — Confirm Endpoint state and credentials, Router binding, Route order, and trusted Selector fields.

2. **Version** — Confirm the expected Guardrail Version and checksum.

3. **Rail and Action** — Inspect Policy, Rule, Rail, Action, Decision, and latency in Runtime logs.

4. **Provider** — Check specialized evaluators, models, networking, and Secrets.

5. **Capacity** — Separate queue saturation, deadlines, and provider latency from true policy failures.

## Runner liveness timeouts

Runner prepares runtime releases on a single background construction worker and publishes them with short, memory-only locks. Verification, NeMo initialization, and snapshot persistence happen before publication. Health checks and existing requests continue using the serving release; a failed preparation leaves that release intact. Model configuration and leased credentials are fingerprinted so unchanged assignments reuse instances, while credential rotation creates a new materialization.

Only versions referenced by enabled Routes with positive target weights are prewarmed. Other verified Artifact definitions remain available to Playground and acquire runtime instances asynchronously on first use. Recent on-demand instances are leased for 600 seconds, with a limit of 128 non-route instances per release; a full leased cache rejects additional cold loads until space is available. Old releases retain their dependencies for pinned calls and close clients after leases and in-flight work drain. Draft previews and validation use the same construction worker and clean up builds that finish after cancellation.

`/health/live` returns a static response on the same event loop as runtime requests. A timeout can indicate a blocked event loop even when the process is still running. A readiness 503 or a startup connection refusal is a different signal; first capture the exact Kubernetes probe failure and container termination reason.

Runner diagnostics are enabled by default and write to the container log:

| Event | What it shows |
| --- | --- |
| `runner_event_loop_stalled` | A watchdog thread detects over 2 seconds of scheduling delay, sampled every 0.5 seconds. Includes the event-loop stack, active lifecycle phases and their thread stacks, RSS, cumulative process CPU time, and available cgroup v2 CPU/memory counters. Repeated warnings are limited to one per 30 seconds during a continuous stall. |
| `runner_event_loop_delayed` / `runner_event_loop_recovered` | Completed scheduling delay / watchdog-observed recovery. The completed delay is recorded even if the watchdog could not run during the stall. |
| `runner_phase_started` / `runner_phase_finished` | Artifact verification, runtime prewarm and provider replacement, snapshot persistence, compilation, validation, and startup restoration. Completion includes duration and result; an unfinished phase helps locate interrupted work. |

Phase metadata contains IDs and counts. Stack diagnostics contain file names, line numbers, and function names, without source lines, local variables, credentials, or request content. A Python watchdog cannot run while a native extension holds the GIL, or when the entire container is frozen or killed. Absence of a warning does not exclude these cases.

Collect both current and previous container logs after a restart:

```sh
kubectl -n <namespace> describe pod <runner-pod>
kubectl -n <namespace> logs <runner-pod> --timestamps --since=30m
kubectl -n <namespace> logs <runner-pod> --previous --timestamps
```

Keep Runner stdout/stderr in your centralized log collector: Kubernetes previous-container logs do not survive Pod deletion. Correlate the failure time with `runtime.prepare_release` candidate counts, `runtime.prewarm` duration, and any unexpected stacks waiting inside `readiness` or `admission_load`. Also compare changes in `cpu.stat` throttling counters and `memory.events` OOM counters, memory usage versus limits, and Kubernetes node pressure. Cumulative CPU counters need two samples to calculate a rate.

Prometheus exposes `guard_runner_event_loop_lag_seconds`, `guard_runner_event_loop_delay_seconds` (histogram), and `guard_runner_event_loop_stalls_total`. For example, `increase(guard_runner_event_loop_stalls_total[5m])` finds watchdog-observed incidents; the delay histogram also captures completed stalls missed by the thread. A blocked HTTP event loop can prevent `/metrics` scrapes, so retain the diagnostic logs as well.

For an isolated performance check, run `.venv/bin/python scripts/benchmark_runner_liveness.py --versions 1 8 32 --repeats 2` from the source checkout. It compares real NeMo prewarm with and without concurrent readiness reads and reports loop delay, CPU time, and RSS. It uses copies of a checked-in fixture and makes no external model calls or cluster changes; results are not a UAT capacity estimate. `--injected-prewarm-seconds` is only for deliberate fault simulation and is labelled separately in the output.
