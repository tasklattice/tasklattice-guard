This guide protects an assistant that answers order questions. The example requires three behaviors:

- Allow ordinary order questions.
- Block requests to reveal internal prompts before the model call.
- Mask customer phone numbers before delivering replies.

Configure and test each behavior. A new Guardrail does not provide these protections automatically.

A **Policy** defines reusable protection through **Rules**. A **Guardrail** combines selected Policies and tests for one scenario. An **Endpoint** authenticates the application. A **Router** selects an exact Guardrail Version. The application applies the returned **Decision**.

<a id="quickstart-before" />
## Before you begin

Use a test environment and an application that you can modify. Review the Rules and Test Cases of the required Policies. A Policy name alone does not establish coverage.

A User account configures business resources. An Administrator prepares platform dependencies, such as inspection models and runtime capacity. An integration developer modifies the caller. Different people can complete these tasks.

<a id="quickstart-steps" />
## Complete the protection path

1. **Prepare a Guardrail.** Select exact Policy Versions. Review enabled Rules, parameters and actions. Run the draft tests. Publish the tested draft as an immutable Guardrail Version.
2. **Create an Endpoint.** Select the protocol for the test application. Issue its Endpoint credential. See [Endpoint setup](/document/developer/endpoint-setup).
3. **Configure routing.** Bind the Endpoint to a Router. Add a Route targeting the released Guardrail Version. Keep the unconditional fallback last.
4. **Submit the Router change.** Preview the matching behavior. Review the versions, weights and Endpoint bindings. Submit the change for another authorized user's approval.
5. **Confirm configuration rollout.** Check that the Router reaches Active. Verify that the Runners applied the desired generation. Review the Guardrail's operating mode.
6. **Integrate and test real requests.** Inspect Input before the model call and Output before delivery. Apply allow, transform and block. Compare application behavior with runtime records.

The [routing guide](/document/operator/operator-routing) explains approval and emergency application. The [gateway guide](/document/developer/gateway-connect) separates non-streaming inspection from streaming Output inspection.

<a id="quickstart-check" />
## Check the completed path

Confirm all of these conditions:

- The Router targets the intended released Guardrail Version.
- The Runners applied the target configuration.
- The Guardrail uses Enforce for this protection test.
- Ordinary questions pass, prohibited Input stops, and matching Output uses the masked text.
- Runtime records identify the expected Endpoint, Router and version.

Monitor and Bypass allow original content. They do not demonstrate blocking or masking. A passing Testing Report does not replace an application test.

<a id="overview-boundary" />
## Product and caller responsibilities

TaskLattice defines and tests protection, distributes fixed configurations and records inspection results. The caller owns business-model calls, sessions and delivery. It must apply the result before content continues.

A personal Access Token calls management APIs. An Endpoint credential calls runtime inspection APIs. These credentials are not interchangeable.

<a id="developer-policy-or-guardrail" />
## Choose the resource to change

| Resource | Question | When to change it |
| --- | --- | --- |
| Policy | How does this detection work? | Existing Rules do not provide the required behavior. |
| Guardrail | Which protections does this scenario use? | Select Policies, parameters, actions and tests for an application. |
| Router | Which calls use which version? | Connect an Endpoint or move traffic between released versions. |

<a id="concept-objects" />
## Distinguish versions and runtime evidence

- A **Policy Version** freezes reusable detection behavior.
- A **Guardrail Version** freezes selected Policy Versions, configuration and tests. Passing tests permits publication but does not create the version itself.
- A **Router revision** freezes routing configuration. Publishing a Guardrail does not update its Targets.
- A **runtime record** describes an actual inspection. It does not establish deployment convergence for every execution node.
