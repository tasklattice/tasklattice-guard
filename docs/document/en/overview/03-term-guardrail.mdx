<strong>What:</strong> A Guardrail is a logical entity. It has two parts:

- **Static part:** a set of Policies and its tests. The tests include the Test Cases that the Guardrail inherits from its Policies, and the custom Test Cases that you add to the Guardrail. A **Guardrail Version** freezes the static part.
- **Dynamic part:** the security events that the Guardrail records when it inspects traffic, and its runtime metrics. You see them on the Guardrail pages in the UI.

Policy, Endpoint and Router are also logical entities. A Guardrail is not a Rule, and it is not a Router.

<strong>Why:</strong> One Policy can serve many applications. A Guardrail selects the Policies that one application needs, and freezes them with their tests in versions that people can review.

<strong>How:</strong>

1. Select Policies in the Guardrail draft.
2. Run the tests.
3. Publish a Guardrail Version.
4. Publish a Router that sends Endpoint traffic to that version.

Readiness and traffic references are shown separately. Different Routers can use different versions of the same Guardrail at once; one Policy count or latest report cannot describe them all.

<a id="glossary-resource-map" />

## Resource relationship map

<ResourceMap locale="en" />

<strong>Keep two relationships apart:</strong>

- A Guardrail binds Policy Versions.
- A Policy contains Rules and Test Cases. Each Rule maps to an implementation. Test Cases verify the behavior.

A production call goes from an Endpoint, through a Router, to one pinned Guardrail Version. The Runner returns a Decision and the evidence for it.

<a id="glossary-term-guardrail" />

## Guardrail

A logical entity for one business scenario. Its static part is a set of Policies and its tests. Its dynamic part is its security events and runtime metrics. After its tests pass, you publish its static part as an immutable Guardrail Version. The [product introduction](#term-guardrail) shows the full relationship.

<a id="export-a-guardrail" />

## Export a Guardrail

To export, use one of these entries:

- On **Guardrails**, open the **Actions** menu of the row and choose **Export…**.
- On an immutable version, choose **Export…**.

Select the released versions to download. The dialog selects no version for you, so the package holds exactly the versions that you select. The package never includes unpublished draft edits. If **Export** is not available, publish a version first.

The release package is a signed `.zip`. Each version in it carries two items:

- Its signed Artifact: the frozen Policy implementations and the compiled configuration.
- Its tests.

The package does not need a Policy Library. It does not include Testing Reports.

To import the package into another Controller:

1. Open the arrow menu next to **Create Guardrail**.
2. Choose **Import release package**.
3. Run the tests of each imported version there. An imported version starts as pending.
4. Release each version after its tests pass.

To run a version, the target environment needs these items:

- A compatible TaskLattice/NeMo runtime.
- The model capabilities that the version declares.
- Credentials configured in that environment.

<a id="term-policy-binding" />

## Policy Binding

<strong>What:</strong> The reference from a Guardrail to one Policy Version. It also holds the settings of this Guardrail for that Policy: the enabled Rules and Rails, the parameter values, and the action overrides. Policy Bindings are part of the static part of the Guardrail.

In most cases you do not tune a Policy in its Binding. The Policy author sets the defaults on each Rule. A Policy is an aggregate of Rules. It also records its compliance sources, which you see on its **Compliance** tab.

<strong>Why:</strong> A Binding turns a reusable Policy into the reviewed behavior of one scenario.

<strong>How:</strong>

1. Configure the Binding in the Guardrail draft.
2. Supply the required parameters.
3. Run the tests.
4. Publish. The Guardrail Version freezes the Binding.

<strong>Example:</strong> Two support applications use the same keyword Policy Version. Each Binding supplies a different `blocked_words` list.

<a id="term-parameter" />

## Binding Parameter

Binding parameter · reviewed value

A Policy value that a person reviews and sets when a Guardrail pins the Policy Version.

Parameters are versioned configuration. Untrusted runtime input should not override them.

For example, an administrator sets `blocked_words` to a list before publishing. A user request cannot change that list at runtime.

<a id="term-guardrail-version" />

## Guardrail Version

<strong>What:</strong> An immutable snapshot of the static part of a Guardrail. It contains the pinned Policy Bindings, Rules, parameters, tests, compiled Artifact, dependencies and checksum.

<strong>Why:</strong> Routing, the runtime baseline and export refer to Guardrail Versions. Each reference names one exact version. No "latest" pointer exists.

<strong>How:</strong>

1. Make sure that the version is released. Test and release an imported version in this environment first.
2. Publish a Router Revision whose Target pins the version.
3. Make sure that the Runners apply the new state.

To serve a different version, submit a Router change that pins it.

<strong>Example:</strong> You publish Guardrail v2. A Router that pins v1 does not move to v2. To change production traffic, review the Router and publish it again.

<a id="term-validation-run" />

## Testing Report

Testing Report · one test run

The record of one run of the Test Cases of a draft or of a version, through the real runtime. It progresses through Queued and Running to Passed or Failed. A completed result is immutable; retesting creates another report. Administrators can delete completed reports after impact review.

- A draft can publish only when all required cases of its current revision pass.
- Releasing a pending version requires its latest completed **version test** in this environment to have passed, matching both its Artifact and frozen test suite. A draft test is not a substitute for this Release action.

<a id="term-checksum" />

## Checksum

Configuration hash · SHA-256

A digest of the immutable compiled configuration.

It proves that the Artifact that runs is exactly the published version.

<a id="user-decisions" />

## Decision: allow, transform, and block

The caller must apply the final Decision. A Decision is not only a risk label.

**Allow / pass**

The content can continue to the next phase.

**Transform**

Use the content that the Decision returns. TaskLattice redacts or rewrites that content, or changes it in a different way.

**Block / reject**

Stop the phase. For blocked input, do not call the model. Do not deliver blocked output.

<a id="term-decision" />

## Decision runtime semantics

allow · transform · block

The final result of TaskLattice for the current phase: allow, transform or block.

The caller must apply the Decision and its action. A Decision is not only a score to show.

<a id="term-enforcement-action" />

## Enforcement Action

Enforcement Action · action after a match

The response that a Rule requests after it matches: allow, block or transform. The Policy sets the default on the Rule. A Policy Binding can override it. [Actions after a Rule matches](/document/overview/glossary-definition#term-rule-actions) lists the three values and their precedence.

An Enforcement Action is not the verdict of an evaluator. It is also not a Python Action that NeMo calls. The integrating caller applies some lifecycle actions.

<a id="term-output-delivery" />

## Output Delivery

interruptible · window buffered · full buffered

How the Runner holds model output until the Output Rail finishes its inspection.

More buffering stops the leak of content that the Output Rail blocks later. It also increases the delivery latency.

<a id="term-failure-mode" />

## Failure Mode

fail-open · fail-closed

The safety behavior when an Action times out or fails.

- **Fail-open** continues and records the evidence.
- **Fail-closed** blocks.

Required inspections often use the conservative behavior.

<a id="concept-boundaries" />

## Authentication, configuration, and execution boundaries

Each component has one responsibility:

- The control plane manages Policy, Guardrail and Router versions.
- Runners do the inspections.
- Applications and gateways make the model calls and apply the Decision that they receive.

Two credential types exist, and you cannot use one in place of the other:

- A Personal Access Token calls the management APIs.
- An Endpoint credential calls the runtime inspections.

Headers or claims that a caller supplies are not trusted identity by default.

Read the role guides as one handoff in this order:

1. Configuration and tests.
2. Endpoint credential assignment.
3. Application integration.
4. Traffic publication.
5. Observation and changes.

The sidebar keeps the order of daily responsibilities.


<a id="glossary-states" />

## Guardrail lifecycle and readiness

<StateLegend locale="en" />

A Guardrail is a stable identity with an editable draft and at most **10 immutable versions**. Imported and locally created Guardrails have the same editing, testing, publishing and deletion capabilities. Package imports also enforce source ownership, including during restoration; see [Deletion and restoration](#guardrail-deletion-restoration). Version configuration, Policy bindings, Artifacts and Test Cases are immutable; local reports, release status and routing references can change.

<a id="state-guardrail-readiness" />

### What Ready means

**Ready means at least one immutable version is Released in this environment and still has a matching Passed report in this system.** Controller matches the Guardrail ID, version, Artifact content digest and frozen test-suite digest. Evidence for another version or another environment does not qualify.

<StateMachineDiagram kind="guardrail-readiness" locale="en" />

- **Ready / ready:** at least one version qualifies. Other versions may be Pending, other reports may have failed, and the working draft may contain untested changes.
- **Not ready / not_ready:** no version qualifies. Examples include a new draft, a passed draft with no publication, imported versions awaiting Release, or removal of the last usable version or its final matching Passed report.
- Ready does not mean every version is released, the current draft passed, Runners are healthy, or requests use it. The most recent report alone does not determine readiness.
- A version that passed but has not been explicitly Released is still Pending and does not make the resource Ready.

<a id="guardrail-registry-columns" />

### What each registry column answers

| Column | Meaning and navigation |
| --- | --- |
| Guardrail | Name and stable ID; opens the detail page. |
| Readiness | Ready / Not ready, derived from retained released versions and local passing evidence. The heading explains the definition. |
| Versions | `2/10` means two retained versions out of ten available slots, with separate Released and Pending counts. Opens the version list. Missing evidence in historical data is shown separately and never counted as Ready. |
| Traffic versions | Exact versions pinned by published Routers with bound Endpoints, plus the runtime baseline. Each Router shows its own Active, Distributing or Failed rollout status and links to its detail page. Version links open that exact version. Unpublished drafts, disabled Routes, zero-weight Targets and Routers without Endpoints are excluded. |
| Updated | The Guardrail resource update time, not the latest test, request or Router update. |

The resource registry does not show a single **Policies** count or **Testing Report** result. Policy counts describe a specific draft or version; reports describe individual local test runs. Inspect them in version details and the Testing Report tab. The version list retains per-version Policy counts and latest test results.

Traffic versions describe desired routing configuration, not observed requests. Even with an Active Router, check Endpoint state and Runtime logs to verify use. Runners or in-flight requests can use older versions during a transition. Multiple versions can serve concurrently; there is no single resource-wide current version. The old Protected label mixed references with readiness and is no longer a Guardrail display state.

<a id="state-guardrail" />

### Resource, draft, version and report are separate

<StateMachineDiagram kind="guardrail-lifecycle" locale="en" />

The diagram uses stored lifecycle values. The resource field `draft / active / disabled` is **not itself UI readiness**. Publishing a draft or releasing a pending version records active; removing or returning the last stored released version to Pending records draft; soft deletion records disabled and deletedAt. A confirmed re-import from the owning source can restore an imported identity to draft. This is not a regular enable/disable switch.

| Scope | States | What determines them |
| --- | --- | --- |
| Guardrail readiness | Ready / Not ready | At least one retained Released version with matching local Passed evidence. |
| Resource lifecycle | `draft / active / disabled` | Publication, Release, deletion and restoration operations; not a live evidence check. |
| Working draft | Untested / Testing / Test failed / Tested / Published | Unpublished changes and the latest draft report for the current revision. A version retest does not test the working draft. |
| Immutable Version | Pending / Released (`pending / ready`) | Local publication or explicit Release, and later evidence deletion or resource deletion. |
| Testing Report | Queued / Running / Passed / Failed | One execution; Passed and Failed are terminal for that report. |

| Operation | Draft and version | Reports, traffic and readiness |
| --- | --- | --- |
| Create in UI | Editable draft, no immutable version. | Not ready; no automatic routing. |
| Test draft | Report binds the draft revision and executed candidate content. | In the normal user workflow, passing permits publication but does not itself create a version. |
| Publish draft | Reuses the tested candidate and freezes Policies, Artifact and cases under its timestamp version. A new version starts Released without a separate Release step. | Ready with retained evidence; Routers stay pinned. The first Default Guardrail publication fills an empty runtime baseline; later baseline switches are explicit. |
| Edit draft | Configuration, runtime profile and Test Case changes require testing the new revision. Renaming the Guardrail or changing its log level does not invalidate draft tests. Existing versions stay unchanged. | Ready remains while a qualifying version exists. Earlier version content is unaffected. |
| Import | Verify signatures and static content, review, then confirm writes. Newly imported versions are Pending. First import seeds an editable draft; incremental imports do not overwrite it. | Reports and source release status do not travel. Test and Release here. Adding Pending versions does not invalidate existing qualifying releases. |
| Retest version | Execute the signed Artifact and frozen cases unchanged. | Generates local evidence. Failure alone does not revoke an existing release. |
| Change Router | Pin an exact version through the change approval and rollout workflow. | Does not change version content, test evidence or resource readiness. Check Router, Endpoint and Runtime logs for delivery. |
| Export | Only selected qualifying Released versions, dependencies and frozen cases enter the signed package. | Reports, runtime logs, routing and baseline pointers do not travel. |

### Immutable Version: Pending and Released

<StateMachineDiagram kind="guardrail-version" locale="en" />

System initialization can also test and publish the built-in Default Guardrail automatically. Testing, test failed, ready to release and retest failed are additional indications, not extra version states.

<a id="guardrail-deletion-restoration" />

### Deletion and restoration

- **Testing Report:** administrators permanently delete a completed report and its results from the detail sheet. Queued and Running reports cannot be deleted. Review the impact first; the transaction checks again. If a retained Released version would have no matching Passed report left, it returns to Pending and its release/load-check metadata is cleared. Another matching Passed report preserves release and replaces the deleted release binding when needed. Deleting a failed report, a redundant pass or a draft-only report does not by itself revoke a valid release. Frozen content, cases and audit remain. References and traffic that prevent version deletion also prevent deleting its final proof.
- **Immutable Version:** deleting a version frees a `n/10` slot. Baseline, published Router, edited Router draft, pending change and pre-approved rollback references block deletion. Calls in the five-minute retention window, recent retirement, and online Runners that have not applied the retiring generation also block deletion. Deleting the version record keeps Artifacts, reports and audit, but orphan reports cannot make a Guardrail Ready. Earlier Router history remains; references to deleted versions cannot be restored directly.
- **Guardrail:** the Default Guardrail cannot be deleted. Published Router references and pending Router changes block deletion; remove these references first and wait for the five-minute call-retention checks to pass. Deletion does **not** remove Router targets automatically. It soft-deletes the identity, preserving ID, static versions, Artifacts, draft, cases, provenance and audit. It permanently clears local reports, queued test requests, stored runtime events and routing-call records, and returns every retained version to Pending. Late test results and telemetry from before the reset are ignored. Unpublished Router drafts and historical references can remain; they do not make the deleted resource usable.
- **Restore by re-import:** currently supported for an imported Guardrail from its original owning source. Explicitly confirm restoration of the same ID in import review. Preserved static content and the working draft are reused; the package does not overwrite that draft. Reports and operational data start afresh, so test and Release again here. Traffic is not automatically restored. A locally created Guardrail with the same ID is rejected by package ownership checks even after soft deletion; re-import is not a universal restore mechanism.

The ten-version limit counts retained Pending and Released records together. Publishing or importing a new version uses a slot; retesting, Release and report deletion do not. Old versions are never removed automatically.

<a id="guardrail-implementation-boundaries" />

### Current differences between checks

The following implementation differences remain; the state definitions above do not mean every entry point uses an identical check:

- **Draft publication:** the UI requires the latest draft report to pass for the current revision. The API currently selects the most recent Passed report for that revision, even if a later run failed or is still running. It still verifies the tested content before creating the version.
- **Version Release:** the UI waits for an ongoing version test; the API checks the latest completed version test. The UI checks the Artifact digest when enabling Release; the API checks both the Artifact and test-suite digests. A repeated Release of an already Released version currently returns it without rechecking evidence.
- **Historical missing evidence:** the resource list recomputes readiness from retained matching reports, but the version badge, Router publication and baseline selection currently trust stored release status without repeating that evidence check. Thus historical inconsistent data can show Released on a version while the Guardrail is Not ready. Export checks the report bound to the release and rejects missing or mismatched evidence. A retest alone does not automatically repair the stored release binding.
- **Deployment baseline package:** when startup is configured to import a Default Guardrail package and the baseline is empty, that startup path currently pins the imported version without checking local tests or Release. The imported version can still be Pending. This differs from the explicit baseline-switch action, which requires Released; it is an implementation gap, not an alternative release workflow.
