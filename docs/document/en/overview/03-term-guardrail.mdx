<strong>What:</strong> A Guardrail is a protection plan for one application. For example, a support-assistant Guardrail might check for jailbreak attempts and sensitive information in replies. In configuration, it uses Policy Bindings to pin Policy Versions and select Rules, Rails, parameters, and post-evaluation directives. It also owns a draft, validation records, and publishable versions.

<strong>Why:</strong> Policies are reusable across applications; a Guardrail assembles them into a reviewable protection boundary with immutable versions. It is neither one Rule nor a Router.

<strong>How:</strong> Select Policy Versions and parameters in the draft, run Validation, publish an immutable Guardrail Version, then route Endpoint traffic to that version. A published Route reference can make the UI show protected, but publication alone does not mean Runners have applied it.

<a id="glossary-term-guardrail" />

## Guardrail

A protection plan for one business scenario. It pins Policy Versions, enabled Rules, Rails, and parameters, then publishes an immutable Guardrail Version after validation. See the [product introduction](#term-guardrail) for the full relationship.

## Export a Guardrail

Open **Guardrails**, then choose **Export…** from the row's **Actions** menu, or
choose **Export…** while viewing an immutable version. Pick the released versions to
download; nothing is preselected, so the package holds exactly what you choose. Unpublished draft edits are never
included. Publish a version first if Export is disabled.

The release package is a signed `.zip`. Each version carries its signed
Artifact (frozen Policy implementations and compiled configuration) and its test
suite, so it does not require Policy Library; test reports are not included.
Import it in another Controller with **Create Guardrail → Import release
package**. Imported versions arrive pending: run their own test suite there and
release them. Running a version still requires a compatible TaskLattice/NeMo
runtime and the declared model capabilities, with credentials configured in the
target environment.

<a id="term-policy-binding" />

## Policy Binding

<strong>What:</strong> A Guardrail reference to one Policy Version plus enabled Rules, Rails, resolved parameters, and directive overrides. Think of it as “how this protection plan uses this capability”.

<strong>Why:</strong> It turns reusable capability into reviewed scenario-specific behavior.

<strong>How:</strong> Configure it in a Guardrail draft, resolve required parameters, validate, then freeze it within a Guardrail Version.

<strong>Example:</strong> Two support applications use the same keyword Policy Version but supply different `blocked_words` in their Bindings.

<a id="term-parameter" />

## Binding Parameter

Binding parameter · reviewed value

A reviewed Policy value resolved when a Guardrail pins its version.

Parameters are versioned configuration and should not be overridden by untrusted runtime input.

For example, an administrator can set `blocked_words` to a list before publishing; a user request cannot rewrite that list at runtime.

<a id="term-guardrail-version" />

## Guardrail Version

<strong>What:</strong> An immutable published Guardrail snapshot with pinned Policy Bindings, Rules, parameters, test suite, compiled artifact, dependencies, and checksum.

<strong>Why:</strong> It is the immutable unit that routing, the runtime baseline and export refer to. Every reference names an exact version; there is no "latest" pointer to follow.

<strong>How:</strong> Make sure the version is released (test and release an imported version here first), publish a Router Revision whose Target pins it, and check Runner convergence. To serve a different version, submit a Router change that pins it.

<strong>Example:</strong> Publishing Guardrail v2 does not switch a Router still pinned to v1; review and republish the Router to change production traffic.

<a id="term-validation-run" />

## Validation Run

Validation record

An immutable result from executing the Test Cases of a draft or of a version through the real runtime.

A draft publishes only when all required cases for its current revision pass; a pending version is released only when the latest run of it here passed.

<a id="term-checksum" />

## Checksum

Configuration hash · SHA-256

A content digest of immutable compiled configuration.

It proves the running artifact exactly matches the published version.

<a id="user-decisions" />

## Decision: allow, transform, and block

The final Decision is something the caller must execute, not merely a risk label.

**Allow / pass**

The content may continue to the next phase.

**Transform**

Use the returned redacted, rewritten, or otherwise transformed content.

**Block / reject**

Stop the phase. Do not call the model for blocked input or deliver blocked output.

<a id="term-decision" />

## Decision runtime semantics

allow · transform · block

TaskLattice's final conclusion for the current phase: allow, transform, or block.

The caller must execute the Decision and action; it is not merely a displayed score.

<a id="term-enforcement-action" />

## Enforcement Action

Enforcement Action · post-detection directive

The specific response requested after a Rule matches, allow, block, or transform. The Policy provides the Rule default, which a Guardrail Binding may override. See [post-match Rule directives](/document/overview/glossary-definition#term-rule-actions) for all three values and their precedence.

It is neither an evaluator verdict nor a Python Action invoked by NeMo; some lifecycle directives are applied by the integrating caller.

<a id="term-output-delivery" />

## Output Delivery

interruptible · window buffered · full buffered

How model output is buffered before Output Rail checks finish.

More buffering prevents leakage of later-blocked content but increases delivery latency.

<a id="term-failure-mode" />

## Failure Mode

fail-open · fail-closed

The safety behavior when an Action times out or errors.

Fail-open continues with evidence; fail-closed blocks. Required checks commonly use conservative behavior.

<a id="concept-boundaries" />

## Authentication, configuration, and execution boundaries

The control plane manages Policy, Guardrail, and Router versions. Runners execute checks. Applications and gateways own model calls and enforce the returned Decision. Personal Access Tokens for management APIs and Endpoint credentials for runtime checks have different purposes and cannot be exchanged. Caller-supplied headers or claims are not automatically trusted identity.

Read the role guides as a handoff from **configuration and validation → Endpoint credential assignment → application integration → traffic publication → observation and iteration**. The sidebar stays ordered by day-to-day responsibility.


<a id="glossary-states" />

## Guardrail state machines

<StateLegend locale="en" />

Color reinforces text: amber means work is in progress or has not converged; green means passed or active; red means failed or action is needed; gray means draft, historical, intentionally disabled, or not started. <strong>Resource lifecycle, immutable-version build state, Runner health, and per-request Decision are separate axes.</strong>

Follow one release to keep them apart: Guardrail Version **Released** means it passed its tests here and can be referenced; a published Route reference can make the Guardrail list show **protected**; Router **active** means default-pool Runners acknowledged the target generation. Finally, check the Endpoint and runtime logs to see whether real requests used that protection.

<a id="state-guardrail-readiness" />

### Guardrail display state: needs testing, ready, protected

<StateMachineDiagram kind="guardrail-readiness" locale="en" />

<strong>Protected (<code>protected</code>)</strong> is a UI projection: the current draft is published, and an enabled Route in a published Router snapshot references this Guardrail as a positive-weight Target. The list currently also requires that Router to have at least one bound Endpoint. Adding a Guardrail to an unpublished Router draft, a disabled Route, or a zero-weight Target does not yield protected. Removing the last qualifying reference returns the list state to ready. Editing the Guardrail draft makes it diverge from the last published version, so the list shows needs testing even while an older version may still serve traffic.

<strong>This is not a traffic-health verdict:</strong> protected reports a configuration reference, not completed Runner rollout, Endpoint availability, or observed requests. The detail page also shows a separate Route-reference badge. Check Router rollout, Endpoint, and runtime logs to verify actual delivery.

<a id="state-guardrail" />

### Guardrail resource lifecycle

<StateMachineDiagram kind="guardrail-lifecycle" locale="en" />

The persisted resource path is draft → active → disabled, with draft → disabled also allowed; disabled is terminal for that resource. Publishing and activating a ready version moves the resource to active. Unlike Endpoint disabling, soft deletion is not a reversible toggle. The <strong>derived display states</strong> `needs_validation / ready / protected` above coexist with this persisted lifecycle. Protected is the Route-reference display state.

<a id="state-guardrail-version" />

### Guardrail Version release

<StateMachineDiagram kind="guardrail-version" locale="en" />

A version has exactly two states: **Pending** and **Released** (`ready`). Its contents, the Policies and the test suite, never change after it is created; releasing changes neither its version number nor its content digest.

- A version published from a draft in this environment is released at once, bound to the passing test run it was published from.
- A version imported from a release package starts pending. Run its own test suite here, against the signed Artifact as it is (nothing is recompiled). Once that run passes, an administrator chooses **Release**, which binds the run to the version.
- Only released versions can be pinned by a Router, set as the runtime baseline, or exported.
- A test that fails after release does not revoke it. The version shows that the retest failed, and people decide whether to change routing.

Released only means the version can be referenced; a Router must still pin the exact version and Runners must apply it. Publishing a new version changes nothing that already references another one.

A version can be deleted once nothing depends on it. **Delete** lists the references first: the runtime baseline, an active Router revision, an edited Router draft, a pending change request, or the pre-approved rollback target of the active change. It also waits until calls that started before the version left routing have finished. Older Router revisions that pinned the version do not block deletion; they stay in history for audit but can no longer be restored. The compiled Artifact and telemetry are kept.
