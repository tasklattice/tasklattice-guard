<strong>What:</strong> An authenticated application, agent, or gateway identity with a protocol entry point; it can bind to one Router.

<strong>Why:</strong> Separate trust boundaries need separate credentials and call context. Caller-supplied headers are not identity.

<strong>How:</strong> Operations creates and issues Endpoint credentials; the integrator calls the matching protocol and verifies setup and runtime health.

<strong>Example:</strong> A support application and an internal test gateway use separate Endpoint credentials, so runtime records can distinguish their calls.

<a id="endpoint-integration-types" />

## Two supported integration types

An Endpoint selects a data-plane integration protocol. The system provides only LiteLLM and Scan. Both use independent Endpoint credentials and let the bound Router select the Guardrail Version.

| Type | Intended client | How it submits checks |
| --- | --- | --- |
| **TaskLattice Guard for LiteLLM** (`litellm-generic-guardrail`) | LiteLLM gateways, or custom gateways and Agents implementing the LiteLLM Generic Guardrail contract | Send `x-api-key` to the Endpoint's `/beta/litellm_basic_guardrail_api`. Use `litellm_call_id` to correlate input and output; the Provider also supports protected WebSocket output. |
| **Scan (F5 compatible)** (`f5-scan`) | Python, requests, curl, F5 Scan evaluation scripts, or applications needing independent text checks | Send a Bearer credential to `/backend/v1/scans`, submit text in `input`, and select request or response with `scanDirection`. Each scan is independent and does not generate a business-model answer. |

Choose LiteLLM for a LiteLLM gateway and Scan for standalone text checks or dataset evaluations. Clients must follow the selected request/response contract and enforce the returned outcome before delivering content. See [setup instructions](/document/developer/endpoint-setup), [LiteLLM request examples](/document/developer/gateway-connect), and [client responsibilities](/document/developer/endpoint-setup#endpoint-delivery).

## Endpoint enablement, setup, and health

<StateMachineDiagram kind="endpoint" locale="en" />

Endpoint has a reversible persisted active ↔ disabled state; soft deletion is a separate overlay. `applying / awaiting_callback / verified / disabled` describe setup progress, while runtime health such as `healthy / waiting / degraded` is observed independently. Neither replaces credentials, Router binding, or real traffic checks. Issuing, rotating, or revoking credentials is also independent of enablement.

<a id="state-credentials" />

## Credentials and per-request results are not resource states

Personal Access Tokens are valid, expired, or revoked according to expiry and revocation timestamps; Endpoint credentials have separate issuance and revocation records. Neither is the lifecycle of a Guardrail or Router. Allow, transform, and block are Decisions for one request, not automatic green or red states on a resource.
