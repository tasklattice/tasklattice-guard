This chapter defines the contract of the **Scan Endpoint** (`f5-scan`). It serves existing F5 Scan scripts, Python requests and dataset evaluation.

- Compatibility covers text scans through `POST /backend/v1/scans`.
- It does not cover F5 project management, history, Scanner configuration APIs or `/scans/raw`.
- The LiteLLM action, Call ID and WebSocket rules do not apply to Scan.

<a id="scan-connection" />
## Address, authentication and routing

```http
POST /backend/v1/scans HTTP/1.1
Authorization: Bearer <Endpoint credential>
Content-Type: application/json
```

- `CALYPSOAI_URL` is the origin of the Runner Service, for example `https://guard-runtime.example.com`. It does not include `/runtime/v1/endpoints/{id}`.
- `CALYPSOAI_TOKEN` is the complete credential that you saved when you created the Scan Endpoint.

All Scan Endpoints share this path. The Bearer credential identifies the Endpoint. The published Router of that Endpoint selects a Guardrail Version.

```bash
export CALYPSOAI_URL='https://guard-runtime.example.com'
export CALYPSOAI_TOKEN='<Scan Endpoint credential>'
curl -sS --fail-with-body -X POST "${CALYPSOAI_URL%/}/backend/v1/scans" \
  -H "Authorization: Bearer $CALYPSOAI_TOKEN" \
  -H 'Content-Type: application/json' \
  --data '{"input":"Text to inspect","scanDirection":"request","flagOnly":false,"verbose":false}'
```

Scan has no `/verify` interface and no model-generation interface. To verify authentication, routing and inspection, submit a real scan.

- A request scan does not call the business model.
- A response scan does not get a model answer automatically.

<a id="scan-request" />
## Request JSON and effective fields

Minimal valid request:

```json
{"input": "Text to inspect"}
```

Request scan with all effective fields explicit:

```json
{
  "input": "Text to inspect",
  "scanDirection": "request",
  "flagOnly": false,
  "verbose": false
}
```

A response scan sends the complete answer that the model already generated, in the same `input` field:

```json
{
  "input": "Here is the generated response.",
  "scanDirection": "response",
  "flagOnly": false,
  "verbose": true
}
```

| Field | Type / default | Constraint and effect |
| --- | --- | --- |
| `input` | Required string | The only content to inspect. It must be a string, not an array, an object or `null`. The schema accepts an empty string, but an empty scan proves nothing about other content. |
| `scanDirection` | `"request"` (default) or `"response"` | Selects the Input Rail or the Output Rail. The value is case-sensitive. |
| `flagOnly` | Boolean, default `true` | `true` reports each match as `flagged`. `false` tells `blocked` and `redacted` apart. |
| `verbose` | Boolean, default `false` | Adds one aggregate result detail of the Guardrail. |

All four fields have strict types:

- `"false"`, `0` and `1` are not booleans.
- An explicit `null` is not the same as an omitted field.
- An invalid enum value or type returns `422`.

Each call resolves the current routing again and returns a new Scan ID. A request scan and a response scan do not share a session or a pinned version. A second submission does a new scan. Scan gives no deduplication or idempotency guarantee. To pin one version for a whole model call, use [LiteLLM](/document/developer/gateway-connect).

`flagOnly` changes how the result shows. It does not change the inspection or the server execution mode. To observe without enforcing, the client records the decisions separately from the delivery. `dry_run` and the compatibility placeholders cannot start a server Dry Run.

<a id="scan-placeholders" />
## Accepted but ignored compatibility fields

| Field | Behavior in this system |
| --- | --- |
| `project` | Not applicable. It cannot select a project, an Endpoint or a Guardrail. |
| `externalMetadata` | Ignored. Routing does not use it, and the response does not necessarily return it. |
| `requestPromptId` | Ignored. It does not link phases and does not reuse an existing Scan. |
| `configOverrides` | Ignored. It cannot override the Scanner, Policy or Router configuration. |
| `disabled`, `forceEnabled` | Ignored. They cannot disable the inspection or force a specific Scanner. |

These fields accept any legal JSON value, including strings, arrays, objects and `null`. The Scan handler also ignores unknown extra fields. All bytes still count toward the body limit. The request below uses the same scan configuration as `{"input":"Text to inspect"}` alone:

```json
{
  "input": "Text to inspect",
  "project": "compatibility-only",
  "externalMetadata": {"dataset": "demo", "row": 1},
  "requestPromptId": "ignored-reference",
  "configOverrides": {},
  "disabled": ["ignored-scanner"],
  "forceEnabled": []
}
```

Keep your own mapping between dataset rows, expected labels and the Scan IDs that you receive. Do not depend on ignored fields to return that information.

<a id="scan-response" />
## Complete response JSON and outcomes

A completed scan returns HTTP `200`, also when a Policy blocks the content. The IDs in these examples are illustrative. The deployed Policies decide the actual results.

A request scan without a match:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "result": {"outcome": "cleared", "response": null, "scannerResults": []},
  "redactedInput": "Text to inspect",
  "scanners": null
}
```

With `flagOnly=true`, a blocking match shows as `flagged`. `redactedInput` can still contain the original text:

```json
{
  "id": "22222222-2222-4222-8222-222222222222",
  "result": {"outcome": "flagged", "response": null, "scannerResults": []},
  "redactedInput": "Text that matched a blocking policy",
  "scanners": null
}
```

The same block with `flagOnly=false` shows explicitly as `blocked`:

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "result": {"outcome": "blocked", "response": null, "scannerResults": []},
  "redactedInput": "Text that matched a blocking policy",
  "scanners": null
}
```

A transformed response scan with `flagOnly=false` and `verbose=true`:

```json
{
  "id": "44444444-4444-4444-8444-444444444444",
  "result": {
    "outcome": "redacted",
    "response": "Email: [REDACTED]",
    "scannerResults": [
      {
        "outcome": "failed",
        "data": {"type": "custom"},
        "startedDate": "2026-10-09T08:00:00Z",
        "completedDate": "2026-10-09T08:00:01Z",
        "scanDirection": "response",
        "scannerId": "55555555-5555-4555-8555-555555555555",
        "scannerVersionMeta": null,
        "message": null,
        "customConfig": false
      }
    ]
  },
  "redactedInput": "Email: [REDACTED]",
  "scanners": null
}
```

| `result.outcome` | Meaning and client behavior |
| --- | --- |
| `cleared` | The required inspections completed without an intervention. Continue according to the result. |
| `flagged` | The scan detected an intervention. The default `flagOnly=true` does not tell a block from a replacement. This is not an allow result. |
| `blocked` | A block, with `flagOnly=false`. Stop the current phase and hold back the original text. |
| `redacted` | A real replacement, with `flagOnly=false`. Use the processed text, not the original. |

`flagOnly=false` does not guarantee only three outcomes. An aggregate intervention without a final block or transform Decision can still produce `flagged`. Handle all four values.

| Response field | Contract |
| --- | --- |
| `id` | A new UUID for each scan. It is not a correlation key and not a model-call ID. |
| `redactedInput` | The string that the scan processed. It can keep the original text when nothing changed. **Its presence does not permit delivery.** |
| `result.response` | Always `null` for request scans. For response scans, the processed text, or `null` when the scan blocks. A text value still needs a check of the outcome. |
| `result.scannerResults` | `[]` when `verbose=false`. When `verbose=true`, exactly one aggregate detail of the Guardrail. It does not list individual Rules or F5 Scanners. |
| Detail `outcome` | `passed` means no match. `failed` means that an intervention matched. It does not mean an execution failure. |
| Detail `scannerId` | The Guardrail ID when that ID is a valid UUID. Otherwise `null`. It is not a configurable F5 Scanner ID. |
| Other detail fields | `data.type="custom"`, the observed start and end times, and the direction of this scan. `scannerVersionMeta=null`, `message=null` and `customConfig=false` are placeholders. |
| `scanners` | Always `null`. Configuration does not apply. |

A timeout, a missing required inspection or an execution failure never becomes `cleared`. Each returns a non-2xx error instead of a successful Scan result.

<a id="scan-errors" />
## Errors, response headers and limits

| HTTP status | `detail.code` | Meaning |
| --- | --- | --- |
| `401` | `invalid_credential` | The Bearer credential is missing, invalid or revoked, or the Endpoint is disabled. |
| `403` | `adapter_mismatch` | The credential is valid, but its Endpoint does not support Scan. |
| `413` | `request_too_large` | The whole body is larger than the limit. |
| `415` | `unsupported_media_type` | The content type is not `application/json`. |
| `422` | None. `detail` is an array. | Invalid JSON, a missing field, or a wrong type or enum value. |
| `503` | `scan_unavailable` | The route or the runtime is not available. |
| `503` | `scan_execution_failed` | A required inspection did not complete or failed. |
| `504` | `scan_timeout` | The scan exceeded its deadline. |
| `500` | `invalid_scan_result` / `scan_internal_error` | The internal result is invalid, or a different processing failure occurred. |

Scan errors other than `422` use this shape:

```json
{
  "detail": {
    "code": "scan_timeout",
    "message": "The scan timed out.",
    "requestId": "66666666-6666-4666-8666-666666666666"
  }
}
```

This `422` example is for a missing `input`. Here `detail` is an array, not the object above:

```json
{
  "detail": [
    {"loc": ["body", "input"], "msg": "Field required", "type": "missing"}
  ]
}
```

Every response from the Scan handler has the headers `X-Request-ID` and `X-TaskLattice-Scan-Compatibility: v1`.

- The success `id` and the error `requestId` are equal to `X-Request-ID`. For `422`, use the header.
- A `401` also has `WWW-Authenticate: Bearer`.
- Errors that a proxy generates do not necessarily use these shapes.

The defaults are **1 MiB** for the request body and **25 seconds** for the scan execution. Configure them with `GUARD_SCAN_MAX_BODY_BYTES` and `GUARD_SCAN_TIMEOUT_SECONDS`, or with the Helm values `runner.scan.maxBodyBytes` and `runner.scan.timeoutSeconds`.

Configure a separate network timeout in the client. Do not count an execution failure as a pass or as a Policy detection. A retry creates another independent scan. See the [Endpoint integration checks](/document/developer/endpoint-setup#endpoint-verification).
