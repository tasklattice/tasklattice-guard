先问一个问题：现有 Policy 只是参数不合适，还是缺少新的检测行为？前者通常在 Guardrail Binding 中调整参数或 Rule；只有确实缺少可复用能力时才自建 Policy。例如多个应用都需要判断“要求泄露系统提示词”这一意图，就适合把检测做成一项 Policy，而不是分别写进每个 Router。

<a id="operator-policy-declarative" />

## 声明式 Policy：先定义规则，再选择如何检查

内建 Policy 和自建 Policy 都使用目录包：一条 Policy 一个目录，一条 Rule 一个 YAML 文件，由 `policy.yaml` 列出规则顺序、测试与资源，统一编译生成运行目录。开发一条 Policy 时，按 **用途 → 多条 Rule → 检测器和参数 → 命中后处理 → 测试** 组织，不需要先学习 Colang。

例如“客服回复不得泄露客户编号，也不得出现内部密钥标签”，可以拆成两条 Output Rule：第一条用 `text/regex@1.0.0` 检查 `CUS-123456` 这样的固定格式，命中时遮盖；第二条用 `text/keyword@1.0.0` 检查 `INTERNAL_SECRET`，命中时阻断。每条 Rule 独立声明风险级别。规则按顺序执行，下一条读取前一条处理后的文本，阻断会结束检查。

Rule 用例用 `scope: rule` 单独验证检测；组合场景用 `scope: policy` 验证完整顺序。测试可以断言 Decision、替换后的精确文本和实际命中的 Rule ID。每条 Rule 的每个阶段都必须有验收用例。

完整示例位于 `policies/examples/customer-information`。在仓库根目录可以运行：

```bash
npm run policies:validate -- policies/examples/customer-information
npm run policies:test -- policies/examples/customer-information
npm run policies:import -- policies/examples/customer-information
npm run policies:export -- policies/custom/customer-information --output /tmp/customer-information.zip
```

导入只接受 `source: custom`，不能覆盖平台内建 ID。目录或 ZIP 包导入后写入 `policies/custom/<id>/`；重新构建并启动 Controller 后，可在 Policy Library 查看并绑定到 Guardrail。**导入不是发布**：还需要完成 Guardrail 测试与发布及路由发布。新版内容须使用新版本号，已发布 Guardrail 保留自己的规则快照。

这条开发路径支持本地检测器的目录／ZIP 导入导出；`npm run policies:regression` 运行全部源包回归，模型用例明确标记为未执行，需在已配置模型的环境中另行测试。新建模型检测器和控制台 YAML 编辑尚未接入。下面介绍的 Policy Studio 仍是当前可编程编辑流程，它的导入按钮使用可编程策略 JSON 包。两种包不能混用。

## 技术原理：从业务要求到检查结果

以“客服回复不得泄露客户编号”为例，先确定 **检查对象** 是模型回复，所以选择 Output Rail；再确定 **判断方式**：结构固定的编号可用已有检测能力，复杂语义则需要已注册的 Action 或专用模型。自建 Policy 的 Colang Flow 负责组织调用和记录结果，Action 负责具体检测或变换。只写“禁止泄露”这样的描述，不会自动产生识别能力。

这条链路中的对象各有职责：

1. **Colang 源码声明 Flow**，例如 `check_customer_id`，说明收到文本后调用什么能力、如何处理其结果。Policy Studio 使用 Colang 2.x；源码由 NeMo 解析，未声明的 Flow、未列入依赖的 Action 或不允许的导入会在运行验证时被拒绝。
2. **Rail Binding 将 Flow 接到输入或输出阶段**，并指定 `detect`（记录判断）或 `mutate`（可能产生替换内容）、不安全时的处理指令、超时和失败方式。由 Rail 与 Flow 名称形成稳定 Rule ID，例如 `flow/output/check_customer_id`。Rule ID 供测试结果和运行记录追溯。
3. **Action Reference 固定可调用能力的名称和版本**。Flow 可以调用 Action Catalog 中已经注册的检测器或模型能力；自建 Policy 不能上传任意 Python 来扩展 Runner。参数在 Guardrail Binding 中解析并随版本固定，不能由生产请求临时改写。
4. **Test Case 证明预期行为**。正常订单回复应放行；包含客户编号的回复应按配置转换或阻断；还要覆盖相似但不应命中的编号、Action 超时等边界。测试写明 Rail、期望 Decision 和覆盖的 Rule ID。

因此，一条自建 Rule 的执行关系是 **Policy Version → Rule（Input／Output Rail 上的 Flow）→ 已注册 Action／模型给出检测结果 → 命中后处理 → Decision**。Policy 定义默认处理，Guardrail Binding 可按应用覆盖；Endpoint 与 Router 决定哪些请求使用哪个 Guardrail Version。完整概念链见[Policy、Rule、实现与处理](#glossary-definition)。声明式目录包统一使用[检测器引用](#term-rule-implementation)；这里描述的 Policy Studio 可编程路径仍以 Flow 作为实现入口。两种入口不能混用导入格式。

## 在 Policy Studio 创建

当前控制台的“新建 Policy”入口位于 [Policy Library](/policy-library)，需要管理员权限。创建时按以下顺序核对：

1. **说明用途与边界**：写清它检测什么、不检测什么，选择保护目录，并确定适用的输入或输出阶段（Rail）。
2. **定义 Flow 和 Rule**：自定义 Policy 使用 Colang 2.x。Flow 名称必须与源码一致；绑定后形成稳定的 Rule ID `flow/{rail}/{flow_name}`。不支持上传任意 Python 作为执行逻辑。
3. **声明运行依赖**：如需调用 Action，选择已注册且固定版本的 Action；需要模型时，先让平台管理人员准备兼容的 Provider、Model 和能力绑定。依赖的 Flow 要放在同一 Rail 的前面，不能形成循环。
4. **设置行为和参数**：区分只检测的 `detect` 与可能返回替换内容的 `mutate`；声明不安全时的处理指令、超时、`fail_open`／`fail_closed` 和可供 Guardrail 绑定的参数。
5. **添加 Test Cases**：同时覆盖正常输入、应阻断或转换的输入，以及边界样例。每条用例写明 Rail、期望 Decision 和覆盖的 Rule IDs。

<a id="operator-policy-release" />

## 验证、发布、使用

下一篇[自建 Policy 的测试、发布与跨环境迁移](#developer-release-transfer)说明验证门槛和版本语义。发布 Policy Version 后，还要在 Guardrail 草稿中绑定确切版本并解析必填参数；单独发布 Policy 不会使任何 Endpoint 请求自动开始检查。修改 Policy 会形成新的草稿和版本，不会暗中改变已绑定旧版的 Guardrail。

跨环境导入的是可编辑定义，不是验证结果；目标环境需要重新检查 Action 和模型依赖、运行测试并发布。

## 为每条 Rule 选择风险级别

在 Flow／Rail 配置中，分别设置 **风险级别** 与 **命中后处理**。新建 Rule 预选“中”，请根据实际业务影响确认或修改。内建 Rule 的默认级别可以在 Policy Library 查看。导入的旧草稿如果没有级别，需要补齐后才能测试和发布。

例如检测客户编号可以按场景设为“中＋遮盖”；检测生产密钥通常设为“高＋阻断”。上线观察时可以在 Guardrail 中把处理覆盖为“仅记录”，事件仍保留原来的高风险。风险级别不能在 Guardrail 中覆盖；要修改级别，应更新 Policy、测试并发布新版本，再更新 Guardrail。[完整分级说明](#term-rule-risk-severity)
