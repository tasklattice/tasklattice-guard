本文的主体是 **Policy Studio 中自建的 Policy**。**测试** 指对当前 Policy 草稿的 Flow、Action 依赖和 Test Case 运行验证。**发布** 指把测试通过的草稿固定成不可变的 **Policy Version**。这里尚未发布 Guardrail Version，也没有切换 Endpoint 流量。

<a id="policy-test-draft" />

## 测试当前 Policy 草稿

1. 为每条 Flow 对应的 Rule 添加必需的 Test Case，写明 Input 或 Output Rail、要检测的内容、期望的 `allow`／`block`／`transform`，以及覆盖的 Rule ID。正常、违规和容易误判的样例都要有。例如，输出“您的订单明天送达”应放行。输出包含客户编号时，应按配置遮盖或阻断。
2. 点击 **Validate & run tests**。控制台先保存草稿并检查配置。然后，健康的默认 Runner 用实际的 NeMo 编译器验证 Colang 源码和 Action 依赖，并执行用例。只通过字段检查或源码编译，都不能代替运行结果。
3. 查看每个用例的实际 Decision、命中 Rule、失败原因和耗时。当前 `draft revision` 的必需用例全部通过，才能继续发布。修改源码、Rail、Action、参数、目录或测试会形成新草稿。旧的测试报告随即失效，需要重新运行测试。

<a id="policy-publish-version" />

## 发布不可变 Policy Version

测试通过后，在 Policy Studio 审查名称、Rail、Action 依赖、Test Case 和超时预算，再发布当前草稿。平台为这个 revision 创建带 checksum 的不可变 Policy Version。后续的编辑会产生新的草稿和版本，不会改写旧版本。Guardrail Binding 必须显式选择需要的 Policy Version，必填参数也要在绑定时解析。

**Policy 发布成功，不等于业务请求已经受保护。** 还需要：

1. 在 Guardrail 中绑定它。
2. 测试并发布 Guardrail Version。
3. 让 Endpoint 通过已发布的 Router 指向这个版本。
4. 确认 Runner 已应用新配置。

步骤分别见[构建并发布 Guardrail](/document/operator/user-lifecycle)与[Endpoint 与 Routing](/document/operator/operator-routing)。

<a id="policy-transfer-environments" />

## 跨环境迁移时重新验证

导出包携带可编辑的 Policy 定义，包括源码、绑定和测试。它不携带源环境的测试报告和发布状态，也不携带目标环境中的 Action 和模型。导入后先核对 Action 名称和精确版本、Provider/Model 能力以及参数，再运行目标环境的 Test Cases，并在该环境发布新的 Policy Version。不要把“源环境已通过”当作目标环境的发布依据。
