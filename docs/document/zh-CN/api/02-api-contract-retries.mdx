调用 API 前，先查看该操作在 OpenAPI 中的权限、幂等和重试说明。网络超时只表示客户端没有收到结果，不代表服务端没有执行。

<a id="api-contract-annotations" />
## 先读懂 OpenAPI 中的三个标记

- `x-token-permission`：调用此操作所需的模块和读写权限。
- `x-idempotency`：重复发送相同请求时，服务端会如何处理。例如，Router 发布使用请求体中的 `idempotencyKey` 识别重复发布。
- `x-retry-policy`：请求结果不确定时，该先查询状态，还是可以重试，以及重试时必须保持哪些内容不变。

这三个 `x-` 字段是 OpenAPI 对操作的说明，**不是**需要随请求发送的 HTTP Header。具体参数以对应操作的请求定义为准。

<a id="api-contract-async" />
## 收到 `202` 后继续查询

`202 Accepted` 表示请求已被接受，异步工作可能仍在进行。例如，创建 Guardrail 验证任务后，使用响应中的 `runId` 请求 `GET /api/v1/test-runs/{runId}`，查看任务结果。不要仅凭 `202` 就向用户报告“验证通过”。

<a id="api-contract-router-publish" />
## Router 变更：按版本操作，再决定是否重试

1. 读取 Router，确认当前草稿及其修订号。
2. 保存草稿：`PUT /api/v1/routers/{id}/draft`。如果响应丢失，先重新读取草稿并比较内容。不要未经审阅就换用更新的 `expectedDraftRevision`。
3. 请求 `POST /api/v1/routers/{id}/publication-preview`，检查这次要发布的版本和 Endpoint 绑定。重新预览时，引用的版本或绑定可能已经变化，需再次审阅结果。
4. 提交变更：`POST /api/v1/routers/{id}/change-requests`，请求体带上已审阅的 `expectedDraftRevision`、`reviewedSnapshot`、`reviewedEndpointIds`、变更说明 `reason` 和可选的变更单号 `ticket`。此时还不会发布。
5. 由另一位管理员批准：`POST /api/v1/routers/{id}/change-requests/{changeId}/approve`，批准后原样发布提交时的快照。紧急情况下可调用 `.../emergency-apply`，填写原因后跳过第二位审批人，系统会记录原因和执行此操作的管理员。

如果提交请求超时，先读取 Router：`pendingChangeRequest` 存在即表示提交已成功。如果批准请求超时，同一位审批人可以重复批准，再检查 `publication.replayed` 和 revision。其他 `POST` 能否重试，要分别查看各自的 `x-retry-policy`。例如，启动测试运行不保证幂等，结果不明时不能自动重发。

<a id="api-contract-resource-ids" />
## 用资源 ID 找到结果

Test Case 用 `/api/v1/guardrails/{guardrailId}/test-cases/{caseId}` 定位。测试运行用返回的 `runId` 查询。不要把 Test Case 的 `caseId` 当成测试运行的 `runId`。
