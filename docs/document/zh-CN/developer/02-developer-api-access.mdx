本章面向自建编辑器、审批流和 CI/CD：通过 Controller API 读取配置、保存草稿、测试并发布版本。实际模型流量的检测，从 [Endpoint 接入指南](/document/developer/endpoint-setup)开始。发布配置不会自动让应用流量经过 Guard。

<a id="developer-control-workflow" />
## 把自己的编辑流程映射到 Controller

1. **读取并显示当前状态**：用 `GET /api/v1/policies/{id}`、`GET /api/v1/guardrails/{id}` 等接口读取现有对象与版本。不要只维护一份与 Controller 脱节的本地副本。
2. **保存候选配置**：按对应资源的 OpenAPI 定义创建或更新 Policy、Guardrail 草稿。让使用者看得出“草稿”和“已发布版本”的差别。要改 Router 时，先读取当前 draft，再调用 `PUT /api/v1/routers/{id}/draft`，并处理并发修订号。
3. **测试并审阅**：提交 Test Case，启动测试运行，按返回的 `runId` 查询测试报告。Router 发布前，调用 `POST /api/v1/routers/{id}/publication-preview`，核对确切的 Guardrail Version 和 Endpoint 绑定。测试通过或预览成功，都不等于已经发布。
4. **发布并确认**：由具备权限的操作者明确批准后调用对应的 publish API。Router 发布要携带审阅过的 `expectedDraftRevision` 和 `idempotencyKey`。收到 `202` 后，继续查询发布和下发状态。审阅后版本或绑定发生变化时，应重新审阅，不能悄悄改用新的修订号。

例如，可以让 CI 在合并配置变更时创建草稿并运行测试，但把生产发布留给审批步骤。Controller 负责校验权限、资源引用和版本约束。**你的系统负责**编辑体验、变更来源、审批规则、并发冲突的呈现，以及向操作者展示最终状态。

## 身份和凭据属于控制面

浏览器控制台用 Session 登录。自建后端或自动化可以使用所属账户创建的个人 Access Token。在 Account → Access Tokens 选择模块的 read 或 write 权限和有效期。密钥只显示一次。创建、列出和撤销 Token，需要所属账户的浏览器 Session。已有的 Token 不能再签发 Token。不要把个人 Token 放进面向终端用户的浏览器代码。

先用 `Authorization: Bearer <token>` 调用 `GET /api/v1/account/identity`，确认 `effectivePermissions`。授权覆盖选中模块的资源。write 包含 read。写操作还要求当前账户是管理员。凭据无效或过期返回 `401`，权限不足返回 `403`。

```sh
curl "{controllerOrigin}/api/v1/account/identity" \
  -H "Authorization: Bearer $GUARD_ACCESS_TOKEN"
```

Endpoint 的运行时凭据（LiteLLM 的 `x-api-key` 或 Scan 的 Bearer Token）只用于[数据面检测](/document/developer/endpoint-setup#endpoint-protocols)，不能修改 Controller 配置。个人 Access Token 也不能代替 Endpoint 凭据检测模型请求。

## 以 OpenAPI 为契约，保留重试边界

`/api/docs` 适合人工查阅。`/api/openapi.json` 可以供自己的编辑器或工具生成客户端。`/api/llms.txt` 是紧凑的索引。每个操作的 `x-token-permission`、`x-idempotency` 和 `x-retry-policy` 分别说明权限、重复请求语义和重试规则。Tag 是产品分组，不等于权限分组。

网络超时不能证明写入没有执行。不是所有的 `POST` 都可以安全地重放。尤其发布 Router 时，要保留同一个 `idempotencyKey` 和请求内容，并核对返回的发布身份。详见[版本化契约与重试](/document/api/api-contract-retries)。
