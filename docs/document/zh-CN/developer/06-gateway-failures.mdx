安全接入的关键不只是请求成功，而是网关在每一种返回下实际交付了什么。运行时的检查记录描述 Guard 的结论，不自动证明你的网关执行了阻断或替换。

<a id="gateway-failure-modes" />

## 区分四种情况

| 情况 | 该怎么理解 |
| --- | --- |
| 有效 `NONE` | 本次检查不要求干预，可使用提交的原文本 |
| 有效 `BLOCKED` 或替换 | 这是正常保护结果；按结果阻断或替换，不能触发 Fail Open |
| 非 2xx、超时、无效 JSON 或无效响应 | 没有取得有效检查结果；按明确配置的失败策略处理 |
| Dry Run | 网关仍调用 Guard、记录结果，但业务流可继续使用原内容；这是网关行为，不是服务端参数 |

**Fail Closed** 在拿不到有效结果时停止业务流。**Fail Open** 只在检查本身失败时允许继续，不能把有效的 `BLOCKED` 改成放行。服务端没有 `dry_run: true` 开关；网关要自行实现观察模式，并分别记录 Guard 决策与实际交付。

<a id="gateway-errors" />

## 常见错误如何排查

- **401**：检查 Endpoint 凭据和 URL；不要改用个人 Access Token。
- **409**：可能是协议、stream sequence、身份、终态或容量冲突；查看 `detail`，不能当作重放成功。
- **422**：请求字段、枚举或形状无效，相关内容尚未完成检查。
- **503**：路由、调用上下文或固定版本不可用；更换 call ID 不能恢复同一次调用。
- **502 / 504（流式）**：检查失败或超时，不等同于正常的 `blocked` 结果。

输入和输出应使用同一 Endpoint、call ID 及一致的路由上下文；关联上下文过期后，输出不应偷偷切到另一个版本。对于已提交但响应丢失的流式请求，不要盲目重试同一 chunk 或新建流假装续接。

<a id="gateway-production-check" />

## 上线前检查

1. `/verify` 成功，并用应放行、应阻断、应替换的样例验证网关真实行为。
2. HTTP 200 后始终解析 action；`BLOCKED` 不再调用模型或交付输出，替换文本按原位置写回。
3. 同一次模型调用的输入与输出共用 call ID；流式输出只交付 `released_text`，顺序、`final` 和终止处理都正确。
4. 明确 Fail Open / Fail Closed 与 Dry Run 选择；把网关交付日志和 Guard 运行记录对照。
5. 与平台管理人员确认已发布版本、Runner 收敛、模型依赖、状态保留时间和多副本共享状态。

仓库中的 `docs/gateway-integration.md` 保留完整字段表、协议边界与可执行验证脚本；本节整理了接入时最关键的行为契约。
