运行日志回答“请求实际经过了哪套保护，得到了什么结果”。例如客服应用报告正常订单问题被阻断：先按 Guardrail、时间范围和“已阻断”筛选，再打开对应的交互，核对 Guardrail Version、输入或输出检查点、命中的 Rule 与执行步骤。Router 的发布状态说明配置是否下发；运行记录才说明某次请求实际发生了什么。

<a id="runtime-log-views" />

## 三种视图各看什么

| 视图 | 用来回答的问题 |
| --- | --- |
| **交互** | 同一次受保护请求整体是放行、转换、阻断还是出错？ |
| **Guardrail 检查点** | 输入或输出阶段的哪次检查得到这个结果？ |
| **系统事件** | Runner 上报了什么运行元数据，例如 Router、决策和延迟？此视图不包含请求或响应正文。 |

页面提供 Guardrail、时间范围、方向和结果筛选；从 Router 的 Monitoring 进入时还可以带入 Route、Target、revision 等路由条件。当前页面没有独立的 Endpoint 筛选器，排查某个调用方时可结合请求 ID、路由上下文和接入方记录核对。

<a id="term-evidence" />

## Evidence：执行证据

这里的 Evidence 是本次检查留下的发现、命中的 Policy/Rule、执行步骤及版本等信息，用于解释 Decision。先看结果和命中规则，再看固定版本、Runner 与错误或延迟；不要把一条“已阻断”记录误读成整个 Guardrail 不健康。

<a id="runtime-log-capture" />

## 为什么找不到某次请求

日志等级决定保留哪些检查点：生产默认的 **Info** 主要记录阻断或失败，**Debug** 还记录转换，**Trace** 才记录全部输入与输出检查点。因此没有查到某次正常请求的详细日志，不能单独证明它没有经过保护。先核对时间范围、Guardrail 与方向，再看 Router Monitoring 和接入方的请求 ID。

请求及响应正文默认不保存。启用相应内容采集后，保留的正文会加密，只有管理员能在日志详情中解密查看；系统事件视图始终不展示正文。
