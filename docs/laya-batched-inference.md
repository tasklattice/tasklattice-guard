# 内置 Laya 合批初判

内置 Laya 在一次本地前向中处理同一检查组的多个初判。每项检查继续保留独立的模型输入、判定问题、阈值、Rule 动作和复核模型。

## 合并范围

- 同一请求、同一输入或输出阶段，编译器已经确认独立且只读的检查组自动合批，无需新增配置。
- 内容安全、越狱和 Topic Control 的常规独立初判可以共享一次前向。PII 使用 Block 等只读动作时也可以加入同一组。
- 脱敏、替换等会改变内容的步骤保留原有顺序；后续检查使用变换后的内容，形成新的批次。条件触发和串行编排仍遵守原有依赖。
- 不跨用户请求、内容块、流式检查窗口或模型实例聚合。不同 token 预算分别处理；聚合上限为 8 项调用、16 个问题，超出时分批。

Topic 的允许/禁止主题字段、PII 的当前内容字段以及安全检查的上下文各自保持原样。只把编码后的问题行装进同一张量批次，不把多个检查的文本或问题拼成新的通用提示词。PyTorch 和锁定的 ONNX 路径都逐项解码各自的结果与截断信息。

## 判定与复核

每个 Rule 继续使用自己的阈值和 `on_unknown`。灰区仅交给该能力、该阶段配置的复核模型：安全类可用 Qwen3Guard，Topic 独立使用聊天模型；Topic 没有复核配置时保留 Laya 结论。

批量张量形状可能使 SDK 四位小数的概率末位变化。当某项批量分数距离其有效上下阈值不超过 `0.0002` 时，只对该项执行一次原输入、原问题的单独核对，再判定是否进入复核。两次推理的用量都保留；核对失败继续走原有错误处理。

单项超时或取消不会撤销其他仍有效的检查。CPU 前向开始后，即使调用方取消，执行许可也保留到计算实际结束。队列按逻辑检查数计入容量；剩余容量只能接纳部分检查时，仍接纳原顺序中可执行的检查，其余各自返回队列错误。单项编码/解码错误独立处理，共享前向失败则该批各项分别记录失败。

证据仍按 Rule 保留。成功合批的 `layaEvaluations[].inferenceBatch` 包含同一物理前向的 ID、成员数、成员序号和问题数；阈值核对成功时另有 `batchThresholdRechecked`。逻辑模型调用记录和 token 用量分别保留，不能用记录条数代替物理前向次数。

## 验证与实测

回归覆盖真实 Controller 编译计划、独立复核、缺失 Topic 复核、截断、阈值核对、隔离、背压、超时与取消；ONNX 分支检查输入张量类型、softmax、行偏移及逐项截断证据。

2026-11-18 在 ARM64、2 核 CPU、6 GiB 内存的隔离 Runner 容器中，对四组独立的合成检查输入测量。它们共有八个 Noul 问题，保留不同的 state 形状。预热后每种方式运行四轮：

| 方式 | 物理前向次数 | 总耗时 | CPU 时间 |
| --- | ---: | ---: | ---: |
| 各项单独调用 | 16 | 8.893 秒 | 17.571 秒 |
| 同组批量调用 | 4 | 8.569 秒 | 16.906 秒 |

单轮四次前向合为一次；本机该样本总耗时降低约 3.6%。问题仍有各自的编码行，计算量不会随调用次数同比下降。最大概率差为 `0.0001`，token 及输入覆盖统计一致。该短合成样本用于检查调度和推理，不代表 Policy 准确率或线上延迟保证。完整记录见 [实测 JSON](laya-batch-benchmark.json)。

使用包含当前代码的 Runner 镜像复现：

```sh
docker run --rm -i --network none --read-only --cpus 2 --memory 6g \
  --tmpfs /tmp:rw,nosuid,nodev,size=64m \
  -e GUARD_RUNNER_CPU_MILLICORES=2000 \
  --entrypoint python "$RUNNER_IMAGE" - --iterations 4 \
  < scripts/benchmark_laya_batch.py
```

该能力随 Runner 更新生效；无需改动现有的独立检查组或复核绑定。
