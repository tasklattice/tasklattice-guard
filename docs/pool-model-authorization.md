# Runner pool model authorization

Pool-token authentication identifies a Runner pool. Model credential resolution now also requires that the pool currently exists and is allocated to an existing tenant group. A stale token-map entry for a deleted or orphaned pool returns no credentials, including candidate validation credentials. The active-credential fetch rechecks allocation in the same SQL statement that retrieves Provider records, so deleting a pool after the preliminary check does not preserve access through that earlier lookup.

Active data-plane Model resolution follows the pool's current **tenant-group Model policy**. Legacy groups retain platform-wide active/activating bindings. Scoped groups receive only the immutable runtime configuration and encrypted Provider snapshot explicitly granted to that group. Blocked groups receive an empty configuration and no active credentials, without fallback. An unknown/unallocated pool receives none. See [group Model configurations](group-model-configurations.md) for the admin UI/API, migration `0065`, validation/fingerprint requirements, distribution and activation guards, and resource bounds. This does not provide per-tenant Provider ownership, dedicated Provider quotas, or isolation between workloads inside a pool.

Candidate Rail-validation leases additionally restrict the Provider reference, expiry and dispatched pool. Migration `0059` stores the encrypted candidate credential snapshot in PostgreSQL, so a different Controller can resolve or revoke the same lease. Issuance uses a database lock and a global limit of 64 live candidates; it prunes expired rows before counting. Requests never create missing leases. Normal completion/error deletes the lease; an issuer crash leaves retrieval available only until its database expiry (95 seconds under a continuous database clock). Expired ciphertext can remain until the next issuance prunes it. All Controllers must share the intended credential encryption key and database.

Before scoped dispatch, the Controller binds the candidate exactly once to the selected pool's current group and allocation epoch, rejecting draining/missing pools, and to the exact current Runner, boot and control session. The credential fetch checks expiry, exact Provider reference, current allocation/epoch/draining and current connected session in the same statement that returns ciphertext. A replacement stream cannot rebind or redeem the old lease. Another replica with the same pool bearer can still redeem a known lease while its dispatch session remains current: session validation is an authorization check, not proof of the HTTP caller's individual workload identity. Provider deletion cascades lease deletion; Provider rotation does not silently replace the candidate snapshot being tested.

Legacy mode without a pool principal retains its existing platform-wide active-credential behavior and can resolve only unbound candidate leases. A pool principal cannot resolve an unbound lease, and the legacy principal cannot resolve a pool-bound lease. An invalid supplied lease never falls back to active credentials. Legacy mode is not a tenant-group isolation mode. Database failure denies retrieval; restoring old database state or moving its wall clock backwards can restore/prolong otherwise expired records and requires credential rotation and fencing in a recovery procedure.

Authorization is evaluated at the database check. A subsequent allocation or session change can race an already authorized response, and a credential already delivered to a Runner cannot be revoked by hiding its reference. Serving lease fencing, short-lived Provider credentials where available, and coordinated rotation are separate requirements. Durable credential retrieval does not make Rail jobs durable, deduplicate dispatch across Controllers, or resume a validation after the dispatching Controller crashes.

Configuration distribution and credential resolution now select the same persisted group grant and snapshot generation under the allocation lock. Provider rotation/source edits require explicit revalidation and regrant; they do not silently change an existing encrypted snapshot. Remaining work includes tenant-owned Provider inventory and budgets, operational fencing/rotation, durable validation-job recovery and complete rollout evidence. Platform-global bindings remain an explicit compatibility mode; they are not silently treated as a group's private inventory.
