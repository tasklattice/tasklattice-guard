# Plan for completing multi-tenancy support

Prepared 29 October 2026 from the [multi-tenancy fact check](multi-tenancy-fact-check-2026-10-28.md), current working-tree code, and the local tenant-group demonstration. This is a design and validation plan, not a claim that the changes are already implemented or that all tenant resources are isolated.

## Target and design choices

The proposed default keeps the existing **tenant group** model. Tenants A and B can share a group and its Runner pool; C can be placed in another group. Within a group, tenants retain separate identities, authorization, resource ownership, telemetry, and configurable admission limits. A group is an operational placement and shared-compute trust domain, not a promise that A and B are protected from a compromised Runner serving both.

Offer a **dedicated isolation tier** by assigning one tenant to a group and deploying its own pool, credentials, pods and, where required by the threat model, network, storage and node/provider resources. A tenant-per-group assignment is necessary for per-tenant Runner-process isolation, but it is not sufficient for infrastructure isolation on its own: Controller, database, Redis, node and upstream providers must also be appropriately separated or protected.

The target should be written as explicit guarantees before implementation:

1. A normal tenant cannot read or change another tenant's private data or use its Endpoint; explicit shares authorize only the permitted operations, including between tenants in the same group.
2. An authenticated Runner can connect only as its assigned pool and access only that group's authorized runtime material. A compromised Runner cannot impersonate a different group. Compromise inside one group can expose that group's in-memory state; stronger same-group compromise isolation requires separate trust domains.
3. Every event, log, decision and cost is attributed to the authenticated invoking tenant, or quarantined if provenance cannot be established. A shared Guardrail's owner is not automatically the caller.
4. Other tenants cannot consume a tenant's agreed admission budget; pods and infrastructure are provisioned according to the selected isolation tier. Measured limits and actual infrastructure constraints are distinguished.
5. Reassignment, revocation, failover and restart must not allow an old Runner to continue serving a reassigned tenant past an enforced and bounded fencing deadline. Where the deadline cannot be guaranteed, fail closed and do not move the tenant.

A shared group cannot promise complete CPU, memory or fault isolation between its members. Hard guarantees against a compromised tenant-controlled workload require one tenant per trust domain and isolated infrastructure; conventional cgroup limits do not alone isolate PostgreSQL, Redis, provider quotas or host failure.

## Phase 0 — Define acceptance and secure the starting state

- Approve the threat model, isolation tiers, availability expectations, data-retention rules and platform-administrator authority. Define which deployments are allowed to use shared groups and which tenants require dedicated placement.
- Inventory all Controller routes, roles, tokens and root/child resources, including policies, packages, Guardrails, Routers, Endpoints, models, shares, users, session/PAT, runtime events, pricing, audit, jobs, artifacts, platform catalog, storage, queues and internal APIs. Map each to owner, authorized shares, actor type, group and cleanup rules. A platform resource is explicitly platform-scoped, not implicitly owned by `tenantA`.
- Turn the audit's confirmed findings into **regression tests that assert the desired secure behavior**. The Runner pool diagnostic still reproduces the legacy shared-token defect; the attribution diagnostic has been converted into a desired-behavior regression for new writes. Neither establishes complete isolation on its own.
- Preserve current access rules for real data while upgrading. Inventory current Runner versions, pool assignments, existing credentials, provider bindings and ambiguous telemetry. Prepare backup, restore and canary rollouts. Do not reset tenants, credentials or historical data to install a migration.

**Exit:** approved resource/permission matrix and negative tests for every supported boundary, with shared or deliberately public resources identified. No default-tenant fallback is silently added to new paths.

## Phase 1 — Bind every Runner identity to its pool

**Problem:** one shared control bearer is accepted while a Runner supplies its own pool ID. The [audit reproduction](../controller/scripts/audit-runner-pool-identity.mjs) demonstrates a cross-pool claim against the real control-server logic with synthetic stubs.

1. Introduce a Controller-managed Runner principal bound to one pool/group. Choose an identity mechanism appropriate to deployment: for example, short-lived workload identity or mutually authenticated certificates whose SAN is mapped to the pool, or pool-scoped bootstrap credentials exchanged for short-lived identities. A shared CA or mTLS by itself is insufficient; authorization must bind authenticated identity to the requested pool. Store only secure verifier/reference material, provide expiry/revocation/rotation, and audit issuance and use.
2. Authenticate the principal before registration. Reject a mismatched `poolId`, unauthorized runner/boot identity takeover, stale credentials, spoofed stream messages and cross-pool desired-state subscriptions. Do not infer authorization from Runner-provided labels or network location.
3. Scope **all** Runner-to-Controller and Controller-to-Runner operations, not only the registration stream: runtime event ingestion, model credential resolution, artifacts, validation and internal evaluation. Separate Controller service identity from Runner identity; check group/pool, capability, current allocation and authorized resource/credential reference at each boundary. Limit provider credentials to current permitted assignments, use short-lived credentials where possible, and avoid turning secret references into an oracle.
4. Replace the global shared Secret in Helm and local provisioning with per-pool/workload identities. Update protocol and generated clients/contracts using repository scripts. Plan issuance, renewal, revocation, restart and a documented recovery path. Existing [control-server.ts](../controller/server/control-channel/control-server.ts), [control-plane.ts](../controller/server/services/control-plane.ts), [app.ts](../controller/server/http/app.ts), [control_client.py](../runner/control_client.py) and chart templates are starting points.
5. Negotiate protocol capabilities and migrate gradually: provision credentials, upgrade Controller, rotate and restart pools, observe authentication failures, then enforce. Legacy shared-token Runners are not considered secure; drain/fence all of them before claiming group security or permitting security-sensitive moves. A rollback must not silently restore a falsely secure state.

**Acceptance:** an authorized Runner connects to its own pool; the same identity cannot claim another existing pool, fetch its desired state/artifacts/credential refs or submit its telemetry, including via HTTP internal endpoints. Test revoked/expired/rotated identities, replay, conflicting runner/boot IDs, reconnects, multiple replicas, misconfiguration and mixed-version rollout. Rerun the current diagnostic as a negative regression.

## Phase 2 — Make reallocation safe through partitions

**Problem:** an offline registration can be inferred from stale heartbeats, while the Runner currently fences on detected control-stream disconnection. Silent or asymmetric partitions and paused processes are not verified.

1. Persist a monotonic allocation epoch and Controller-issued, pool-bound serving lease. Registration and restart begin fenced; the Runner activates a complete snapshot for the current epoch and acknowledges it before receiving a serving lease.
2. Renew only on authenticated Controller acknowledgement. Runner enforces a **monotonic** local deadline on every request path, including HTTP, WebSocket/streaming, and internal work; on expiry fence new work, cancel or safely terminate in-flight work, and invalidate or prevent serving stale cached artifacts. A late, replayed or reordered acknowledgement cannot extend service beyond a deadline derived from its request start. Health/metrics remain distinguishable from serving readiness.
3. For a move, under a database transaction and the same group/pool allocation lock, stop issuing old leases and advance the epoch. Drain or revoke all prior members and wait for every old lease to expire, including a justified clock/drift/scheduling margin, before allowing the new epoch and destination to serve. State the exact assumptions under which Controller time, monotonic Runner timers and delays are bounded; use conservative server-side expiry and no renewal on uncertainty. Coordinate replicas and Controller failover.
4. Migration enables safe leases on all relevant Runners before security-sensitive moves. Controller/identity issuer outage means leases expire and serving stops; communicate the availability tradeoff. Old Runners without fencing cannot be treated as safely drained simply because the UI says offline.

**Acceptance:** fault-injection tests cover detected and one-way partitions, packets dropped in either direction, delayed/reordered/replayed renewals, Controller restart/failover, database outage, node pause/restart, event-loop stalls, clock changes and multi-replica reassignment. Verify no overlap of old/new authorization, in-flight and stream behavior, recovery and fail-closed behavior. Test actual clusters in addition to unit tests. An arbitrary unbounded delay or a malicious Runner ignoring its lease cannot be made safe solely by application timers; infrastructure/network fencing or workload termination is needed for that threat model.

## Phase 3 — Trusted tenant provenance and evidence isolation

**Problem:** [tenant-context.ts](../controller/server/services/tenant-context.ts) derives event tenant from Endpoint → Router → Guardrail owner → `tenantA`. The [isolated attribution diagnostic](../controller/scripts/audit-tenant-attribution.postgres.test.ts) reproduced wrong event and cost ownership for a shared-Guardrail Playground-shaped request. It did not itself demonstrate sensitive data exposure in a live browser.

1. Introduce a trusted invocation context with caller tenant, group/pool, endpoint/router or Playground origin, policy/Guardrail version, request/call ID, expiry and lifecycle. For internal Playground, validation and asynchronous jobs, the Controller persists an opaque invocation ID or issues a scoped signed context and sends it to Runner. Runner echoes the context; ingestion resolves and validates it server-side against the authenticated Runner pool and allocation. Do not trust tenant IDs in client headers, request body, or arbitrary Runner telemetry.
2. For ordinary runtime requests, derive identity from the authenticated Endpoint and its pinned assignment. Verify ownership, current group and immutable pin across input/output, streaming, retries, enrichment and completion. Check consistency with the context and scope; never let an untrusted tenant pick an attribution ID.
3. Remove the generic `tenantA` fallback and owner-as-caller behavior. Reject or quarantine unattributable/conflicting events and costs as platform-only, with operational alerts; do not expose them to a tenant by guessing. Handle asynchronous retries, idempotent event IDs, cursor scope, cost rollups, audit, tracing and retention using the same trusted identity. Ensure encrypted content can be decrypted only under authorized scope.
4. Inventory historical events/costs, including shared Guardrails and missing resource IDs. Reassign only with reliable provenance; quarantine ambiguous records, and define review, retention and audited remediation. A database migration cannot infer a missing caller reliably. Correct dashboards without overwriting historical facts.

**Acceptance:** end-to-end A invokes C's explicitly shared Guardrail: A sees its own event/log/cost and C does not see A's invocation merely by ownership. Include external Endpoint control, Playground, validation jobs, block/transform, missing/unknown/forged context, cross-pool conflict, duplicate/reordered enrichment, empty and concurrent calls, and tenant-bound pagination/cleanup. Test both persisted SQL and live API/UI. Phase 1 is a prerequisite for trusting pool provenance; a compromised Runner may still fabricate data within its own trusted group unless the design authenticates the invocation independently.

## Phase 4 — Close application and database authorization gaps

1. Separate **tenant actor**, explicitly scoped **platform administrator**, and explicitly authorized **background/service principal**. A missing tenant context must not automatically authorize a request or default its ownership to tenantA. Replace broad internal bypasses with narrowly scoped jobs and audit them. Make public health/status contents intentional and minimize information leakage; require authentication for metrics in production configuration.
2. Complete the route/resource matrix from Phase 0: both lists and direct IDs; read, create, edit, publish, delete, share, revoke, export and credentials; children and versions; tenant-owned versus platform/global models; PAT scopes; redacted errors; route bindings and cross-owner references. Recheck access at publish/use time and revocation, not only at creation. Same-group membership must not imply resource sharing.
3. If the agreed requirement includes database-enforced defense in depth, add PostgreSQL row-level security with non-owner, non-superuser application roles, `FORCE ROW LEVEL SECURITY` where appropriate, explicit policy for roots, dependent children, evidence, share lookups and platform resources, and narrowly granted worker/admin roles. Bind actor identity per transaction using `SET LOCAL` or equivalent on the same connection; clear it reliably across pooled sessions and rollback. Avoid broad BYPASSRLS roles for ordinary requests. Address composite ownership constraints and migrations for existing data.
4. Design operational access, tenant deletion/export, backups, recovery and retention so that tenant data and encryption keys follow the intended boundary. RLS helps with SQL-level defense; it does not isolate host, Redis, provider secrets or compute.

**Acceptance:** automated owner/share/admin/PAT matrix with positive and negative reads/writes across every route and child type, A↔B in the same group and A↔C across groups, spoofing, stale grants, concurrent revocation, guessed IDs and background jobs. If RLS is enabled, test direct SQL as each non-superuser role, tenantless context, transaction rollback, pooled connection reuse and admin/worker operations with no silent bypass. Run real IdP and production authorization integration separately.

## Phase 5 — Real tenant/group admission and usage controls

1. Add Controller-authoritative tenant ownership to the Endpoint runtime configuration and carry it from successful Endpoint authentication through routing, admission, pinned context, telemetry and cost. A client header must not choose the tenant. Extend the protocol, desired-state filtering and tests accordingly.
2. Define policy and units: group and tenant concurrency, requests/second or rolling windows, burst and queue limit, guard calls versus end-to-end pipelines, input/output and streams, cancellation, provider tokens/calls, budget periods, priorities, and whether unused capacity can be borrowed. Set explicit behavior for limit rejection (`429`/bounded wait and retry hints where appropriate), fairness, timeouts and outage. Do not present planning parameters as enforced limits.
3. Implement hierarchical admission at the Runner/gateway boundary after authentication, with bounded per-tenant queues and fair scheduling. Across multiple replicas, use a correctly atomic, distributed coordinator or partitioned budgets with safe lease expiry, so aggregate limits are not multiplied by replica count. Define release on timeout, cancellation, crash and long-running streams. Expiry alone is not enough to reclaim a permit while the old request can still run: workers must renew and cancel or fence work on renewal failure; use unique lease IDs and epochs to prevent stale release or double counting. Reconcile conservatively after a crash. Decide fail-closed versus explicitly bounded degraded operation if the coordinator fails. Keep independent provider request/token/spend controls where provider capability supports them.
4. Add admin APIs and UI to assign limits and show actual use, queues, rejections, expirations and per-tenant p95 using trusted attribution; expose unavailable metrics rather than fabricate them. Roll out in observe-only mode before enforcement. The lab's current reference slots, group reservation and quota simulation remain labeled as test-generator behavior until they are replaced by measurements of enforced production admission.

**Acceptance:** a sustained peak from A cannot prevent B from obtaining its configured capacity under defined load and limits, including A/B in the same group and C in another. Verify both single and multi-Runner replicas, streams, bursts, idle borrowing, cancellations, coordinator crash/partition, misbehaving clients and accurate counters. Use controlled input rates and record dropped/rejected/unfinished work alongside latency. Provider limits and infrastructure contention are separately measured.

## Phase 6 — Provider, storage, network and infrastructure isolation tiers

- **Providers and models:** introduce explicit platform, group or tenant scope for provider connections, model definitions, active bindings, credentials and billing; preserve legacy global resources as explicit platform scope. Distribute only the configuration needed by each pool. Permit sharing only under explicit policy. Authorize credential resolution by principal plus assigned model/version; support per-scope rotation and audit. Dedicated upstream accounts/credentials and hard spend limits depend on the provider's capabilities.
- **Provisioning:** registering a group or pool in Controller does not create a Kubernetes workload. Choose external platform/GitOps provisioning first or build an operator with reconciliation; verify registered pool, Service, workload identity and readiness agree before admitting traffic. Autoscaling and safe deprovisioning need their own ownership and fencing rules.
- **Runner pods:** use separate pools/pods and Kubernetes cgroups for groups; select one tenant per group for dedicated Runner isolation. Set requests, limits, namespace quotas, service accounts and Pod security. If physical CPU/memory/host failure independence is required, provision dedicated nodes or independent clusters and test the scheduler/eviction behavior. A CPU limit without capacity reservation or node separation is not an availability guarantee.
- **Redis:** partition keyspace and credentials with access control/TLS, or use separate Redis instances for stronger boundaries. Validate cross-group key access, connection reuse, expiry, recovery and malicious Runner assumptions. Shared Redis may still create a shared availability bottleneck.
- **Database and backups:** use scoped roles/RLS for shared tables or dedicated databases/clusters where required. Separate credentials, keys, backups and recovery according to tier; test that an operator can restore/delete one tenant without exposing another.
- **Network:** define an enforceable policy for Controller, Runner, Redis and provider egress by namespace/workload identity. Confirm the selected CNI actually enforces NetworkPolicy; test forbidden ingress/egress and DNS/metadata paths. ClusterIP alone is not an isolation boundary.
- **Operations:** isolate or accurately attribute logs, metrics, traces, audit and rate budgets; protect admin operations with least privilege and controlled support access. Define failure domains and incident procedures, credential rotation and tenant lifecycle automation.

**Acceptance:** test each claimed tier against its threat model: compromised tenant credentials, compromised group Runner identity, denied network/secret access, noisy neighbor, database/Redis failure, backup/restore, operator access and node eviction. Clearly state shared services that remain common dependencies. A/B may continue in one group for shared-compute testing; the dedicated tier needs at least one tenant per pool and stronger infrastructure where required.

## Phase 7 — Deployment, evidence and release gate

1. Run focused tests first, then full Controller/Runner suites, typecheck/build and regenerated OpenAPI/protocol contract checks. Run migrations against populated pre-group data, including upgrade and rollback; verify all background workers, context propagation and live UI. Fix regression fixtures without weakening assertions.
2. Run an adversarial and performance matrix on a representative **multi-node staging environment** with realistic policies/provider configurations and multiple replicas. Capture exact resource versions, topology, workload, expected/observed outcomes and screenshots; separate isolated fixtures, live checks and hypotheses. Verify observability and no secret exposure in evidence.
3. Canary: deploy Controller and capable Runners, provision identities and scopes, backfill provenance, enable lease/fence enforcement, observe quotas, then enforce per tier. Require all old insecure Runners drained and every claimed security boundary independently validated. Roll back only to a state explicitly labeled insecure or unavailable; do not silently widen access.
4. Release only when confirmed cross-pool identity and attribution regressions are fixed and the chosen tier's acceptance tests pass. Record residual shared dependencies and known limitations. Commit/push only when the user's release condition is met; the current worktree and local-only secrets remain uncommitted.

## Blockers and decisions

**Using the definition that work compatible with the existing tenant-group design is implementation work rather than a blocker, no known architecture blocker prevents implementing the intended group-based multi-tenancy.** Pool-bound identities, attribution, fencing, authorization and quotas are unfinished and prevent claiming the feature is complete today, but they can be implemented without replacing tenant groups or changing the principle that A/B may share a Runner group.

The remaining constraints apply only to specific stronger guarantees or validation. In particular, a tenant group is a shared Runner trust domain by design. Complete recovery of historical attribution is impossible for records whose original caller was never captured; quarantine can protect access going forward, but cannot recreate missing facts. The small local environment can implement and smoke-test functionality but cannot demonstrate multi-node HA or physical isolation.

| Topic | Current status | What is needed |
| --- | --- | --- |
| Runner pool identity | **Confirmed security defect; implementation work.** Shared bearer permits another pool claim. | Pool-bound identity across all control/internal APIs, rotation and negative tests (Phase 1). |
| Shared-Guardrail Playground evidence | **Confirmed attribution defect; implementation work.** Isolated ingestion reproduced owner attribution. | Trusted invocation context, quarantine and live regression (Phase 3). |
| Safe moves under partition | **Unverified safety property; implementation and testing work.** Detected-disconnect tests alone do not prove a bounded fence. | A lease/fencing design with explicit timing assumptions and fault injection (Phase 2). |
| Isolation scope | **Conditional design conflict.** A/B sharing a process is incompatible with a requirement for hard process isolation between them; this does not block group-level isolation. | Decide whether groups are trust domains and which tenants require one-tenant groups, dedicated infrastructure or separate clusters. |
| Quotas and availability | **Implementation work and configuration decision.** No enforced per-tenant CPU/memory/rate/spend guarantees are present. | Choose units, bounds, fairness, burst, coordinator failure behavior, provider budgets and availability targets. |
| Pool provisioning | **Implementation or operational choice.** The current group API records allocation but does not create or scale Runners. | Choose manual/GitOps deployment or implement a controller/operator; verify workload identity, routing and lifecycle against pool assignment. |
| Infrastructure and budget | **Validation blocker for strong availability/physical isolation claims.** Local kind has one CPU and about 1.93 GiB memory; two reduced Runners already use substantial capacity. | Provision representative multi-node staging and realistic workloads, plus budget/placement policy. The local stack remains useful for narrow functional tests and screenshots, not HA/capacity certification. |
| Identity and secret infrastructure | **Implementation/deployment choice.** There is no already-established pool-bound issuer in the current design; scoped pool credentials are one compatible starting option. | Choose workload identity/mTLS issuer or scoped credentials, provisioning/rotation/revocation and fallback for non-Kubernetes deployments. |
| Historical attribution | **Genuine limitation for exact historical correction.** Some existing events do not contain a reliable invoking tenant; no implementation can infer information that was never recorded. | Decide quarantine, retention, review and remediation; do not silently invent ownership. |
| Providers and billing | **Conditional external dependency.** A shared upstream account may not provide hard tenant-level quotas or dedicated availability; this does not prevent application-level tenant controls. | Confirm provider IAM, scoped credentials, rate and billing features; buy separate provider capacity/accounts if required. |
| Git delivery | **Integration dependency.** At audit time the local branch's recorded upstream was 18 commits ahead and one behind, with substantial uncommitted work. | Inspect current remote and reconcile without rewriting others' work after security gates pass. Do not force push or commit local secrets/evidence accidentally. |

Identity, attribution, fencing, admission, application authorization and group provisioning can be developed and tested locally without changing the tenant-group design. The current local environment blocks only convincing multi-node/HA and physical-isolation validation. Exact correction of records with missing historical provenance remains impossible; and a demand for hard isolation between tenants in the same Runner process would conflict with the selected shared-group principle.
