# Guardrails 评测平台第一版设计

日期：2026-10-08。状态：设计草案。

本平台面向银行隔离 UAT 环境，用固定版本的数据向已暴露的 Tali Guard Endpoint 发送请求，验证返回结果是否符合预期、受控并发下的响应延迟，以及在遥测可用时的模型调用成本。支持人工分析和发版流水线，评测材料通过导出、审批、导入进入目标环境。

第一版内部采用 Dataset、Target、Scorer、Run 四个核心对象；桌面产品只提供“数据集、测试目标、测试记录”三个主要入口。评分规则进入测试配置，报告归入测试记录。数据选择和执行配置在启动 Run 时冻结；Suite 和独立 Experiment 暂不引入。执行证据与评分分开保存，同一批响应可以重新评分，无须再次调用 Guard。

## 产品边界与用户心智

用户只需回答四个问题：请求发到哪里、测试哪些数据、什么结果算正确、这次测试的表现如何。测试目标是一个可调用的 Endpoint 接入配置。Profile、Guardrail、Policy、Router、Route 和其发布版本由 Tali Guard 管理，不成为 Testing 的导航、必填字段或独立管理对象，也不要求用户先选择“评测 Profile 还是 Guardrail”。

日常路径为：选择已保存的测试目标 → 选择数据集和预期规则 → 设置重复次数及可选历史对照 → 启动 → 查看报告。首次使用时录入 Endpoint URL、接入协议和凭据；导入数据时确认样本字段与标签。连接配置和离线材料审批可以复用，后续启动只检查其有效性，不要求每次重新配置或自行声明批准。

报告默认回答“这个 Endpoint 在本次条件下的结果”。用户可以给测试记录添加业务名称或备注，例如“银行默认配置调整后”；此类标签不作为服务版本已被验证的证据。比较对象是两次 Run，支持同一 Endpoint 的前后比较以及不同 Endpoint 的对照。

Tali 专用 Adapter 封装协议、请求构造、响应解析、关联 ID 和输出阶段上下文准备。LiteLLM 或 Scan 接入必须匹配实际 Endpoint 类型；不要求普通用户编辑 JSON 模板或学习内部执行计划。第一版先实现经联调确认的一种协议，其余按接入能力逐项开放，不把所有协议标为已支持。

内部版本、模型依赖和路由命中信息可以随响应或可选只读遥测连接自动收集，保存在 Run 的执行证据里。界面默认只显示“执行环境证据：完整 / 未提供 / 发现变化”，原始字段在“排查详情”按需展开。无法取得这些字段时仍可完成 Endpoint 的行为评测；成本或版本归因相关结论按各自证据标明缺失。不得声称已经验证某一 Guardrail 或 Profile 的改善。

同一 Endpoint 出现多种执行配置时保留整体服务指标；如已配置需要固定环境的比较条件，则暂停相应归因结论或门禁，并提示“检测到执行环境变化”。重复结果不同只说明响应存在波动，不能一律归因为模型随机性。Testing 不自动修改 Tali 的路由或部署配置，也不通过内部 Controller 接口绕过用户选择的 Endpoint。

## 自建范围与已有工具

自建的价值在于银行评测流程的整合：离线材料交付、审批与版本追溯、标签复核、Guard 执行证据关联，以及符合客户权限边界的桌面分析界面。

promptfoo 已提供配置驱动评测、Assertions、Web UI 和 CI 集成，也支持对已有输出执行评分。UI 本身不足以成为自建理由；需要验证已有工具能否直接满足上述客户流程。[配置与 UI](https://www.promptfoo.dev/docs/configuration/guide/)、[Assertions 与已有输出评分](https://www.promptfoo.dev/docs/configuration/expected-outputs/)、[CI 集成](https://www.promptfoo.dev/docs/integrations/ci-cd/)。

garak 可提供扫描及逐次请求和检测结果的报告，适合作为后续攻击测试来源或执行适配器。[garak 报告](https://reference.garak.ai/en/stable/reporting.html)。

建议自建管理、证据和审批集成层，保留可替换的 Executor 与 Scorer 接口。技术选型先用同一组离线样本验证固定版本的 promptfoo 执行适配器，比较关联 ID、原始响应保留、重复执行、取消和离线运行能力。只有实际存在的接口缺口才由自有 Worker 补齐。第一版不承诺 promptfoo 完整配置兼容，也不重新实现通用攻击生成器或负载测试引擎。

## 四个核心对象

| 对象 | 必须保存的内容 | 版本规则 |
| --- | --- | --- |
| Dataset | 原始样本、规范化样本、输入与标签哈希、原始标签与来源、风险分类、split、许可与来源信息 | 发布版本不可修改；更正标签产生新版本 |
| Target（界面称测试目标） | 名称、Endpoint URL、接入协议、环境、凭据引用；Adapter 版本及映射由接入实现管理 | 接入配置版本不可修改；实际观测的服务证据另存于执行记录，不要求用户选择内部受测版本 |
| Scorer（界面称评分规则） | 实现标识与版本、配置、标签到预期的映射、断言、输入要求、输出契约、可选 Judge 配置；在测试配置中选择与查看 | 独立建模和版本化；实现和配置均参与摘要；依赖或 rubric 改变产生新版本 |
| Run | 选定样本清单、Dataset 和 Target 版本、执行参数、初始 Scorer、门禁与 baseline 的冻结快照 | 执行配置不可修改；执行记录与后续评分追加保存 |

Report 是 Run 下指定 ScoringRevision 的视图和导出产物。ScoringRevision、CaseExecution、Attempt、AnnotationReview 和 ApprovalReceipt 是持久化的从属记录，不要求用户另外管理顶级对象。

Run 快照必须保存最终选中的样本 ID 及哈希，不能只保存会随数据变化而重新求值的筛选表达式。Target 快照只保存凭据引用和版本，不保存明文凭据。实际凭据由运行环境绑定。

baseline 引用固定的 `run_id + scoring_revision_id`，启动时解析并冻结。后续重新评分、数据纠错和“设为 baseline”均不改写已有 Run 的引用。再次运行可以直接从历史 Run 复制配置并生成新 Run，不依赖 Suite。

## 执行与评分分离

执行器负责生成请求、调用 Target 和保留证据。Scorer 消费固定的样本标注与执行证据，输出评分。Report 和 GateEvaluation 引用这些结果。

```text
DatasetVersion + TargetVersion + RunConfigSnapshot
                       ↓
            Run → CaseExecution → Attempt
                       ↓
               不可变执行证据
                       ↓
ScorerVersion + 标签版本 + 评分配置
                       ↓
                ScoringRevision
                       ↓
          Report + BaselineComparison + GateEvaluation
```

每次 Attempt 保存实际提交内容或其受控存储引用、上下文、方向、发送和完成时间、客户端耗时、HTTP 状态、经过凭据清理的响应头与响应体、Adapter 版本及解析结果。执行异常、协议异常与内容动作分开记录。缺失响应不以空字符串替代。

执行状态为 `queued / running / completed / failed / canceled`。全部计划调用已结束并不代表评测通过；必须另存计划数、实际发送数、有效响应数、超时数和未知执行结果数。Worker 崩溃后的在途请求可能已在 Target 执行，不承诺跨系统 exactly-once，也不能把重新发送当成无成本恢复。

评分结果建议包含 `pass / fail / error / not_applicable / insufficient_evidence`，以及 score、reason、断言结果、证据引用和所用版本。业务分类的 safe/unsafe、动作 allow/block/transform 和评分 pass/fail 是不同字段。

一个 Scorer 是带版本的评分实现，Assertion 是本次配置中的具体条件，例如预期动作、类别匹配或替换文本不得含指定实体。标签映射属于评分配置的一部分，不能隐含在 Endpoint Adapter 中，也不能从受测 Guard 的响应倒推预期。

第一版提供确定性评分器及经过部署审批的扩展接口。客户需要 LLM Judge 时，必须显式配置 UAT 可访问的模型，并冻结模型标识、rubric、参数和评分依赖；没有可用模型则返回评分错误，不回退到公网服务。不能从导入的数据或 YAML 自动执行 JavaScript、Python、模板代码或远程插件。

重新评分创建新的 ScoringRevision，保存 Scorer、标签版本、解析版本、评分时间和操作者。原始执行证据、旧分数、旧报告和旧门禁保持不变。若新的 Scorer 需要未留存的证据，则标记证据不足；重新评分本身不得补发 Target 请求。重新解析原始响应也需要记录新的 Adapter 版本。

标签单独纠错且实际请求内容和上下文未变时，可对旧响应使用新标签版本重新评分。若样本内容、请求构造或上下文变了，必须生成新 Run。比较 baseline 与 candidate 时，两侧必须使用相同评分及标签口径，不能只给 candidate 换规则。

## 质量指标与标签口径

输入审核使用 prompt 的标签，固定输出审核使用对应 response 的标签。新生成的回答不能继承数据集中原回答的标签。缺失标签、不可用内容和不能映射的样本保留排除原因和计数；风险类别不直接替代二元安全标签。

| 指标 | 口径 |
| --- | --- |
| 检测质量 | 有实际检测结论时，以风险为正类计算 TP、TN、FP、FN、Recall、FPR、Precision、F1；分母为有有效参考标签和有效检测结果的观测 |
| 策略动作符合率 | 实际动作及必要的内容断言符合冻结预期的可评分观测数 / 可评分观测数；错误脱敏不能仅凭 transform 动作判为通过 |
| 执行覆盖率与错误率 | 计划、已发送、已结束、有效、错误、超时分别计数；失败和缺失同时进入完成率门禁 |
| 分组结果 | 按风险类别、语言、输入/输出及标注来源展示；多标签样本在每个类别可参与一次，总体不能重复计算 |

只提供动作的 Target 可以评测动作符合率及按预期动作定义的误拦、漏拦；不得声称测得内部分类器的准确率。技术故障导致的保护性阻断也不能当成正确风险识别。总体结果使用预先固定的样本权重，Accuracy 作为补充，同时报告样本数、有效覆盖率和适用的区间。

## 非确定性与版本比较

Run 支持全局及按样本设置 `repeat_count`。一次计划重复对应一个 CaseExecution，其网络重试另建 Attempt，并记录原因、序号和关联关系。重复采样与故障重试不能互相替代，也不能把多次重试当成多个独立样本。

默认不自动重试。启用时冻结允许重试的错误类型、次数、退避和最终结果选择规则；不因内容评分失败而重试到通过。保留首次失败，未知是否已执行的请求不自动重发，成本包含可归属的全部实际尝试。

第一次执行和每次计划重复都使用新的调用身份；同一次业务调用的 Input 与 Output 可以按契约共享 call ID。随机种子只控制本平台的样本选择和顺序，不能承诺消除远端模型随机性。

测量随机波动时禁用评测客户端的响应缓存；记录 Target 缓存和采样参数，不能关闭或未知时在报告中标明。重复执行得到同一个缓存结果，不是独立的模型采样。promptfoo 已有全局和逐样本 repeat 配置，且其文档明确说明独立调用与缓存设置的关系，可作为适配参考。[重复测试配置](https://www.promptfoo.dev/docs/configuration/test-cases/#repeating-an-individual-test)。

对样本 i 定义：

- 通过率 `p_i = 评分通过的计划重复数 / 可评分的计划重复数`，同时列出计划重复数及缺失数。
- 行为不稳定：至少两次有效重复中出现不同的规范化检测结论或动作。文本措辞变化本身不算行为不稳定。
- 评分不稳定：固定同一份 Target 响应，多次 Judge 评分出现不同结果；与 Guard 行为不稳定分别统计。
- 观察到的不稳定样本比例：出现行为不一致的样本数 / 至少有两次有效重复的样本数，并展示该分母占计划样本数的覆盖率。

`repeat_count = 1` 时不稳定性显示“未测”；观察到零次不一致只表示本次重复中未发现波动。不同 N 的不稳定比例不可直接比较。N 按运行预算配置，少量重复用于筛查，不将某个小 N 宣称为统计充分的标准。

总体通过率按样本预设权重聚合 `p_i`，不能因为某条样本重复更多而获得更大权重。错误和缺失另报并参与完成率门禁，不能通过剔除失败请求提高发布结论。

baseline 比较要求相同的样本内容、标签、评分器、方向和兼容的重复计划。按样本比较通过率、阻断概率和动作分布，展示差值与不确定性；不要仅用一次 pass→fail 判定退化。聚合区间按 case，或同源 conversation/behavior 分组重采样，避免把 N 次相关重复当成 N 个独立案例。预先定义统计方法及适用范围；极小样本或极端事件下区间方法不适用时标为证据不足。

可交错执行 candidate 与 baseline，以降低服务时段差异。对历史 baseline 保留执行环境、时间、并发和版本信息。无法确认实际受测版本、版本中途改变、样本缺失或统计证据不足时，不得给出已验证改善的结论。逐样本差异用于调查，单条显著性结论需额外处理样本量和多重比较。

## API 与发版门禁

UI 和无界面调用使用同一套 API、权限和审计。以下为新评测平台的建议契约，不是现有 Guard 接口：

| API | 行为 |
| --- | --- |
| `POST /api/v1/runs` | 接收数据、Target、Scorer、repeat、并发、门禁和 baseline 引用；冻结配置，返回 202 与 run ID |
| `GET /api/v1/runs/{id}` | 返回执行、评分、遥测补齐状态和计数 |
| `POST /api/v1/runs/{id}/cancel` | 停止派发新请求，保留在途及已完成记录 |
| `POST /api/v1/runs/{id}/scorings` | 使用留存证据创建新的 ScoringRevision |
| `GET /api/v1/runs/{id}/scorings/{revision}/report` | 返回机器可读汇总、固定 baseline 差值及门禁结果 |

创建 Run 和重新评分均支持幂等键：同一个键与同一请求返回原任务，同键不同内容返回冲突。API 服务账号只访问授权 Dataset、Target 和结果；触发评测权限与编辑 Target、导出原文、审批变更权限分离。

门禁配置包括绝对阈值和相对 baseline 的退化限额，例如各关键类别漏检率、误拦率、错误率、完成率及 p95。阈值、指标分母、置信要求、缺失数据处理和 baseline 身份在启动前冻结，不设置未经客户确认的统一合格线。

门禁状态为 `pass / fail / inconclusive`，并逐项给出实测值、阈值、差值、样本量和理由。发布集成只有 pass 返回成功；fail 与 inconclusive 均阻止自动通过，但保留原因差异。没有有效 baseline 时不能静默跳过已配置的退化门禁。

流水线通过 API 创建 Run、轮询或等待完成、读取固定评分报告，然后映射退出码。第一版提供可离线运行的调用示例，JSON 报告为必需，JUnit 可作为导出格式。评测只能给出发布判定，不自动发布 Guard 配置。成本为可选门禁；未配置成本插件时可不启用，但已要求成本验收而证据缺失时必须返回 inconclusive。

## 延迟范围

第一版执行器提供最大并发和必要的请求间隔，采用闭环受控执行，不承诺目标 RPS、容量极限或开环负载结果。

客户端延迟从实际发送请求到完整响应或错误结束，排除任务排队、样本导入、评分和后续遥测补齐。保存逐次 Attempt 的耗时，计划重复的最终耗时另含其重试及退避。超时按实际观察和阈值报告，不伪造完整响应时间。

报告 p50/p95/p99、计数、错误率、并发、输入长度、缓存和预热条件，按放行、阻断、干预、异常分组。结果仅代表该运行条件下的观测。容量验证后续接入专用工具；本平台不在第一版实现开环调度或 coordinated omission 修正。

| 数据面调用入口 | Scan 使用 `/backend/v1/scans` 与 Bearer 凭据；LiteLLM 使用对应 Endpoint 下的 `/beta/litellm_basic_guardrail_api` 与 x-api-key；系统仅提供这两种 Endpoint | 使用实际提供的完整 URL 与匹配协议；不以 Profile 或 Guardrail ID 代替 Endpoint 地址 |
| 客户端关联身份 | LiteLLM 接收 `litellm_call_id` 并转换为内部 call ID；Scan 每次独立执行，忽略 requestPromptId | LiteLLM 按协议将 Attempt ID 映射到调用字段；Scan 以服务端返回的 id 关联测试记录 |
| 实际执行身份 | 通用响应的 `ProtectionDecision` 包含 `guardrail_id`、`guardrail_version`、`router_id`、`route_assignment`、`effective_release_id`、`model_revision_id` 等可选字段 | 自动留存为扩展证据；不同协议的可用字段分别验证，不作为用户创建测试的必填配置 |
| Endpoint 作用域 | `_scoped_call_id` 为 call ID 增加 `{endpoint_id}:` 前缀 | 遥测查询使用作用域内 ID；记录映射，不以裸 case ID 跨重复调用复用 |
| 遥测关联 | `_emit_telemetry` 的 `requestId` 使用内部 call ID，`id` 优先使用当前 OTel trace ID，否则为生成的 UUID | `requestId`、事件 `id` 和 trace ID 不可混为同一个概念 |
| 查询入口 | `GET /api/v1/telemetry/events` 支持 `requestId`、`endpointId` 和方向筛选；服务按 requestId 精确匹配 | 需 Controller 运行时读取权限、网络连通性、分页及异步等待；作用域内 requestId 需满足接口 256 字符上限 |
| 执行 trace | 列表仅返回摘要；`GET /api/v1/telemetry/events/{id}` 默认详情保留 `metadata.trace` 和 `usage` | 可以取得结构化执行证据；这不等于提供任意 OTel/Tempo span 的通用查询 API |
| 采集与原文 | `_telemetry_metadata` 构造决策的 trace/usage；日志等级及加密配置决定原文采集 | 原文采集与结构化 metadata 分开；不能认为必须打开原文采集才能查询执行 trace |
| Token 与重试 | trace 节点包含模型、input/output tokens、重试和耗时 | Token 字段可能缺报；节点是否重复聚合、每次重试用量是否完整需要联调确认 |
| 货币成本 | 已查看的 RuntimeUsage 与遥测映射没有直接货币成本字段 | 只能在用量完整且有固定价格表时估算；不能声称返回已结算费用 |
| `litellm_trace_id` | 请求模型接受该字段，本次搜索未发现它参与该链路关联 | 不作为已验证的 trace 传播或查询依据 |

源码索引：[请求模型及事件构造](../runner/api.py)、[遥测查询路由](../controller/server/http/app.ts)、[查询及详情服务](../controller/server/services/control-plane.ts)、[运行事件来源](../controller/server/services/runtime-log-source.ts)、[权限映射](../controller/server/http/token-permissions.ts)、[异步事件导出](../runner/telemetry.py)、[Token 字段语义](../proto/tasklattice/guard/control/v1/evaluation.proto)、[调用生命周期](gateway-integration.md)。

建议的 TaskLattice Cost Provider 流程：生成短 Attempt ID → 根据协议映射到 `call_id` 或 `litellm_call_id` 后调用 → 按作用域 requestId 和 Endpoint 查询 → 获取匹配方向的事件详情 → 解析执行错误、模型用量和版本证据 → 追加 CostObservation。Input 和 Output 属于同一业务调用时按既有契约共享 call ID，但仍分别保存 HTTP Attempt 和阶段证据。

查询结果还可能包含 Controller 推导的 completion 故障事件，不能把每条结果都算作新的模型调用。遥测通过 WAL 异步传送，采用有截止时间的补齐任务；缺失时显示 pending 或 incomplete，并保留查询窗口和原因。

不要对整个 Run 复用一个 OTel trace ID：当前事件 `id` 优先取当前 trace ID，数据库以该字段为主键并忽略冲突，可能导致后续事件因主键冲突被丢弃。适配器使用每次 HTTP 调用独立的 trace 上下文，run/case 关系在评测平台维护。联调必须包含重复样本、Input/Output 和重试的事件唯一性验证。

同一业务调用的 Output 可能依赖之前 Input 建立的版本与路由上下文；孤立 Output 可能返回 `call_context_expired`。不能通过删除 ID 把这种失败伪装成成功。输出评测适配器的上下文准备能力作为独立接入验收项。

## 可选成本插件

Target 的必需能力只有请求调用与结果解析。Cost Provider 单独配置和授权，第一版可启用 TaskLattice 遥测适配器，也允许第三方 Target 没有成本来源。未来可接入响应内 usage、供应商计费记录或受控的离线成本文件。

每条 CostObservation 保存 `run/case/execution/attempt` 关联、来源与版本、模型、用量、货币、价格表版本、计量范围、observed_at 和证据引用。状态区分 `not_configured / pending / complete / incomplete / error`，数值为 `null` 时不转换成 0。

Token 乘以价格表标为估算成本；供应商计费记录标为报告费用；自托管 GPU 分摊另设口径。汇总必须处理重试、回退、缓存计费及多模型调用，避免父子 trace 节点重复计费。无法确认某个零值代表未调用还是未上报时，标为用量不完整。

成本统计分别展示总额、已覆盖请求数、覆盖率、每千次逻辑检查成本及每次 HTTP Attempt 成本，明确分母和是否包含准备请求与重试。部分请求缺失时只展示已观测金额及覆盖范围，不推断完整总成本。

Scorer 使用 LLM 的费用记录为评分成本，与 Guard 模型调用成本分开。执行完成后成本仍可补齐，但已导出的报告和门禁结果保持固定；补齐数据后生成新的报告快照及门禁评估，不回写审批证据。

## 银行 UAT 的离线交付与安全边界

服务、前端资源、数据库、Worker、评分实现及可选 Judge 均应能在断网环境启动和运行。部署材料包含固定版本的镜像和依赖；运行时不从 CDN、包注册表、Hugging Face 或公网模型服务获取必需资源。外发遥测默认关闭。

Dataset 导入首先支持离线包。包内至少包含 manifest、schema 版本、稳定 sample ID、数据文件、每文件摘要、来源和许可、Dataset 父版本、变更说明及样本输入与标签摘要。原始资料和规范化数据分别保留。Hugging Face 仅是可选的准备端数据来源，其 revision、split 和字段映射在生成包时冻结。

公开基准优先固定评测 split，登记受测模型可能的数据重叠；客户 UAT 另保留未用于调参的业务集。数据集名为 test 不代表对所有模型都独立。Aegis 的缺失 response 和 REDACTED 样本须在导入预览中明确处理，不能作为普通文本悄悄计入评测。

导出包冻结内容摘要后交审批，审批回执绑定该摘要、目的环境、变更范围和审批身份；导入验证审批证据和可信签名或客户指定的审批机制。单纯校验文件哈希不能证明材料已经获得授权。导入先预览差异，再落地为不可变版本，不能自动执行评测。

第一版保存审批回执并验证绑定关系，可对接银行既有流程，不必重建完整审批系统。Dataset、Scorer、Run 配置模板和报告均可按权限导出；Target 的环境地址和凭据引用在 UAT 重新绑定，绑定改变要在最终执行快照和相应审批范围中可见。包内不含可直接使用的 Target 密钥或解密密钥。

| 边界 | 第一版要求 |
| --- | --- |
| 有害内容与客户数据 | Dataset 原文、响应和导出分别授权；按组织或项目隔离；访问、标注、下载和导出可审计；存储加密及保留周期 |
| 审计 | 记录操作者、时间、对象与版本、动作、理由和审批依据；审计条目不重复写入全文、密钥；访问和修改权限分离 |
| Target SSRF | 由管理员批准的环境白名单约束域名、IP/CIDR、端口和协议；允许明确批准的 UAT 私网目标；阻止元数据、loopback 和未批准地址 |
| 网络连接 | 仅允许批准的 HTTP/HTTPS；解析并校验 IPv4/IPv6，连接时约束已批准地址，防止 DNS 重绑定；默认禁用重定向，启用时逐跳复核；使用出口网络策略约束实际连接 |
| Target 凭据 | 凭据使用密钥管理服务或独立挂载密钥加密，数据库只存密文或引用；Worker 在执行时取用，普通 API 不返回明文；请求证据和日志清理敏感头 |
| 配置执行 | 默认只接受声明式配置及批准的评分实现；导入不能触发脚本、shell、远程下载或不受控文件读取 |
| 文件与页面 | 校验归档路径、文件大小和解压上限；有害文本按纯文本显示，不能当 HTML 或模板执行；CSV 导出处理公式注入 |

SSRF 控制也覆盖在线 Dataset 下载、HTTP Scorer 和 Cost Provider，不能只保护 Target 表单。凭据的加密密钥不能与密文一起进入导出包；轮换和重新绑定保留审计。客户自己的审批要求在部署验收时固定，不能用“支持导入导出”替代审批绑定。

## 标签复核与数据版本

样本详情提供“提交标签复核”。用户选择原始标签错误、策略映射错误或证据不足，填写建议值与理由，可附执行证据。Guard 与标签不一致只是复核线索，不自动证明标签有误。

复核队列采用 `submitted / in_review / accepted / rejected`。经授权的复核人查看原始样本、标注来源、预期规则与重复结果，保留裁决及理由。发布 Dataset 新版本与提出修改的权限分开，并按客户要求绑定导出审批。

原始标签错误生成 Dataset 新版本；策略映射错误生成 Scorer 或评分配置新版本，不修改来源标签。保留旧标签、原始来源、新标签、复核人、时间和父版本关系。Aegis 的 response 标注含人工、LLM jury 和拒绝增强来源，可用来筛选复核优先级，但不能仅因模型标注就自动判错。[Aegis 字段说明](https://huggingface.co/datasets/nvidia/Aegis-AI-Content-Safety-Dataset-2.0#dataset-structure)。

纠错界面展示受影响样本数、历史 Run、内容哈希是否变化，以及可重新评分还是必须重新执行。旧评分和已审批报告继续引用旧版本。对外比较使用统一的已复核标签版本，且报告披露与原始基准标签的差异，避免把纠错隐藏成模型提升。

## promptfoo 配置兼容边界

以版本化转换器支持一个明确列出的配置子集，先验证 `tests.vars`、基础文本或 JSON 请求模板、已批准 HTTP Target 映射、确定性 assert、repeat 和最大并发。各字段只有在语义等价且完成对照验证后才标记为支持。

导入输出标准化 Run 配置和兼容性报告，逐项显示已转换字段、警告和不支持项。遇到不支持的 Assertion、动态表达式、文件引用、hooks、自定义 provider 或代码必须明确拒绝，不能忽略后继续运行。已批准的扩展以单独版本化部署包提供。

审批、成本来源和标签纠错信息保存在平台的配套 manifest，不伪装成 promptfoo 原生字段。导出只生成经过验证的兼容子集；无法表达的内容列入配套说明并禁止声称无损兼容。兼容测试使用同一组固定请求和响应，对比转换前后的请求字节、评分结果、repeat 语义及错误分类。

执行器选择不改变证据和评分模型。即使使用 promptfoo 执行，平台仍保留原始 Attempt、ScoringRevision 和审批证据，并锁定执行器与转换器版本。

## 桌面交互与第一版验收

桌面导航采用“测试记录、数据集、测试目标”；标签队列归入数据集，报告与历史评分归入测试记录。Scorer 是独立领域对象，在新建测试的“预期与评分规则”中选择、查看或保存规则版本，无须独立一级导航或在线脚本编辑器。创建测试时选择目标、数据、预期规则和重复次数；并发、可选历史对照和门禁进入执行设置。启动前展示请求预算和已有接入校验状态，校验失败须说明原因及处理入口。

测试目标页面只管理连接信息及可选成本来源，禁止加入 Profile、Guardrail、Policy、Router 的编辑或发布入口。接入检查说明其实际覆盖范围：凭据验证成功不等于业务请求已通过完整保护链路；发送一次样本检查属于真实调用，要显示样本及可能消耗。缺少 Controller 管理权限不阻止使用有效 Endpoint 凭据进行行为与延迟测试。

Run 详情先显示执行覆盖率、评分状态、质量指标及门禁，再展示逐条结果。样本行同时显示各重复的结果分布，提供误报、漏报、行为不稳定、评分不稳定、执行错误和标签待复核筛选。成本不可用显示明确状态，不以空白或零值掩盖。

第一版验收应覆盖以下完整路径：

1. 在无公网访问的 UAT 中，导入带审批证据的离线 Dataset 和评测配置，完成本地凭据绑定。
2. 用 API 发起带 baseline 和重复执行的 Run，关闭浏览器后任务仍继续；幂等重试不创建第二个 Run。
3. 对固定响应使用另一个 Scorer 版本重新评分，Target 调用计数不增加，历史评分与门禁保持不变。
4. 展示样本重复结果、观察到的不稳定比例及有效重复覆盖率；证据不足不会显示已证实改善。
5. 通过同一冻结门禁评价 baseline 与 candidate；失败或证据不足均阻止自动通过，输出机器可读原因。
6. 为 TaskLattice Target 验证唯一调用身份、Endpoint 作用域、Input/Output 方向、列表到详情查询、token 缺报、重试用量、异步到达和失败 completion 的处理。只有通过后才声明成本插件可用。
7. 第三方 Target 无成本插件仍能完成质量与延迟评测；启用成本门禁但数据缺失时返回 inconclusive。
8. 从误报或漏报提交标签复核，经裁决发布新 Dataset 版本，使用统一标签重评 baseline 与 candidate，保留旧报告。
9. 验证未批准的 Endpoint、DNS/重定向绕过、越权查看或导出、可执行导入内容和含密钥包均被拒绝并留下审计证据。
10. 仅持有 Endpoint 地址和运行时凭据的用户，无须理解或配置 Profile、Guardrail、Router，即可完成目标接入、数据选择、评分和报告查看。没有成本接入时显示“未接入”，不显示 0。
11. 服务版本证据未提供时保留 Endpoint 行为报告；若观测到执行环境变化，显示对应证据并限制受影响的版本归因或门禁，不静默归因于模型波动。

实现前的最小技术验证是：用批准的 UAT 测试 Target 完成“唯一调用身份 → 原始响应 → 遥测详情 → 固定评分 → baseline 门禁”的单条及重复样本闭环，并记录哪些证据实际可得。其结果决定 TaskLattice 成本插件的承诺范围和执行引擎的最终选型。
