# Historical audit attribution quarantine

Migration `0007_audit_attribution_quarantine` preserves audit records while removing their tenant assignments. Earlier attribution selected the actor's tenant, even when a platform administrator acted on another tenant's resource; some background and platform activity also fell back to tenant A. Those assignments are not reliable proof of which tenant may read the details.

The former assignments are preserved in the internal `historical_audit_attribution` table for operator review. Ordinary tenant audit lists omit records with unknown ownership; platform-wide audit queries retain access to all records. Tenant audit history therefore decreases at upgrade. The former tenant ID alone is not sufficient evidence to restore a record: do not bulk-restore it to recover historical totals. A supported review, audited remediation, and retention workflow still needs to be built.

New tenant-resource audit records derive ownership from the authoritative resource, rather than the actor. A resource share allows the recipient to use or view the shared resource, but does not grant visibility of its owner's audit trail. Platform resources, unresolved resources, and administrator access-token activity are platform-only. Controller-produced policy-deletion audits capture the owner from the locked resource before hard deletion; the application must not accept this ownership value from a request. Other deleted or unknown-resource events without reliable owner context are platform-only.

Back up the database and plan migration duration based on audit volume. **Stop all old Controller writers throughout the migration and keep them stopped:** older code or a replay of older migrations could reintroduce actor-based attribution or the tenant-A default. The migration takes a write-conflicting table lock, saves the previous assignments and clears them in one transaction, and records a checkpoint so replay does not quarantine newer records. Do not roll back to older ingestion code while claiming tenant isolation.

If Policy IDs have conflicting owners across legacy and current tables, the shared authorization helper, hard deletion, and package import now fail closed rather than choosing an owner. The broader Policy resource and child-record paths still need an audit: some queries check an individual root and then select versions, reports, or other child records by Policy ID. Do not assume those paths are protected by the shared helper until each has been verified or changed to handle conflicting ownership.
